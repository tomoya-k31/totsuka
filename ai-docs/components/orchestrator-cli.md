# 責務

ユーザー向けの CLI 表面。`clap` でコマンドを解釈し、[orchestrator-core](/components/orchestrator-core.md) のユースケースを呼び出す。

# 公開インターフェース

- bin 名: `totsuka`
- `plugin`（#52）: `install <dir> [--yes] [--enable]` / `install --bundled <name>|--all [--yes] [--enable]` / `uninstall <name>` / `enable <name>` / `disable <name>` / `list [--json]`。install は取得元と SHA-256 を表示し確認を要求（§5.4）、GitHub Release からの取得は v1 未対応（ローカルディレクトリからの install に案内）。`list` は `ORIGIN` 列（`bundled` / `copied`、`--json` では `origin`）で**ファイルがどこから来ているか**を出す（#611）。
  - **`--bundled`（#345）**: リリース tarball が `totsuka` の隣に置く `plugins/<name>/{<name>, plugin.toml}` からパス指定なしで入れる。探索順は「起動に使われたパスの隣」→「symlink 解決後のパスの隣」の各々について `plugins/` → `../libexec/totsuka/plugins/`（後者は将来の prefix 形式インストール用）。採用したツリーは必ず表示する。**#611 で「コピーする」から「同梱由来と記録するだけ」に変わった**（[ADR-0067](/decisions/adr-0067-bundled-plugin-resolution.md)）: ストアにはマーカー 1 ファイル（`bundled`）しか置かず、manifest とバイナリは起動のたびに同梱ツリーへ解決される。**同梱ツリーのパスは保存せず `current_exe` から計算する**ので、Homebrew が旧 Cellar を消しても腐らず、`brew upgrade` 後に入れ直すコマンドが要らない。ただし **hidden `--bundled-dir <path>` を渡した場合は従来どおりコピーする** —— 実行時解決は走っているバイナリから導くため、運用者が指定した別ツリーを指さないので、黙って違うものへ差し替わるよりスナップショットを取るほうが正しい。同梱由来の記録があるのに同梱ツリーが無いビルド（`cargo install` 等）では「未インストール」ではなく `NoBundledTree` を返す（宣言は健全で、無いのはツリーのほうなので修理の向きが違う）。**`std::env::current_exe` は macOS で symlink を解決しない**（`_NSGetExecutablePath` は起動に使われたパスを返す。Linux の `/proc/self/exe` とは異なる）ため、`fs::canonicalize` の結果も明示的に探索する — 標準のインストール形（`/usr/local/bin/totsuka` → `/usr/local/lib/totsuka/totsuka` の symlink、プラグインは**リンク先**の隣）はこれが無いと 1 つも見つからない。同梱ツリーが無いのは `cargo install` 由来のビルドでは正常なので、エラー文はディレクトリ install へ案内する。上書き用の `--bundled-dir` は hidden（env 変数を使わないのは、未知の `TOTSUKA_*` が stderr に警告を出し（[ADR-0009](/decisions/adr-0009-env-override-whitelist.md)）stderr を JSON として読む E2E を壊すため）。
  - **`--from-source <name>|--all`（#346）**: totsuka のチェックアウトからビルドして install する開発用の経路。`--repo <dir>` で明示、省略時は cwd から上へ辿って「Cargo ワークスペースのルート**かつ** `plugins/` を持つ」ディレクトリを探す（`git rev-parse --show-toplevel` は**使わない** — 無関係なクローンでも答えてしまい、その後で分かりにくく失敗するため）。`cargo build [--release] -p <pkg>... --bins` を **1 回**だけ起動し（target ディレクトリのロックを 1 度で済ませる。`--bin` を列挙しないのは arch-lint が「プラグイン 1 個 = bin 1 個」を保証しているため）、`prepare_install_from` には manifest として `plugins/<pkg>/plugin.toml` を、バイナリの**ディレクトリ**として `target/<profile>` を渡す（ファイル名 `<name>` は `prepare_install_from` が manifest の `name` から付ける）— **staging ディレクトリを組まない**。`--profile release|dev`（既定 release）、`--print-plan` で cargo を起動せず計画だけ印字。CLI が `cargo` にシェルアウトするのは既に `git` / `op` で行っている作法の範囲内で、`scripts/` に置くとチェックアウトの無い環境で使えず名前→パッケージの対応と config 編集を複製することになるため CLI 側に置いた。
  - **`--enable`**: install と enable の概念分離（F-56）は保ったまま、1 コマンドで両方やるオプトイン。`<dir>` 指定でも `--bundled` でも `--from-source` でも使える。書き込みは `plugin enable` と同じ raw テキスト編集なので、コメント・整形は維持される。**`--enable` 指定時は何も書く前に config.toml の読み取り+パースを preflight する** — 編集はストア更新の後なので、preflight が無いと「インストール済みだがコマンドは失敗」という部分適用が残る。**#175: パス解決・設定ロードは他コマンドと同じ `Cx` 経由**（独自の `Locations` は廃止。`--config` / `TOTSUKA_*` env オーバーライドが plugin コマンドにも効く）。設定欠落時: `install` / `uninstall` / `list` は**空設定で続行**（`Cx::load_config_or_default` — 宣言の照合にしか使わないため `totsuka setup` 前でも動く）、`enable` / `disable` は**エラー**（編集対象ファイルが無いため。`→ run totsuka setup` を案内）。
- `run [--watch] [--dry-run] [--secrets-stdin] [--json]`（#63/#462）: **`--secrets-stdin`（#754、[ADR-0099](/decisions/adr-0099-secrets-stdin.md)）は設定ロードより前に** stdin の 1 行目を `common::install_supplied_secrets` で読む（端末・改行前の EOF・値が文字列でない JSON は exit 4。EOF は待たない。dry-run でも読む）。以降このプロセスは `secret:<name>` をその値で解決し、ストアを指す参照はすべて拒否する。メインループの CLI 表面。設定ロード→`config::validate`（Error があれば起動拒否）→ログ初期化（§5.2）→単一インスタンスロック（F-74、dry-run は読み取り専用のため取得しない）→**フックアセットの書き出し**（core の `hooks::install` 呼び出し、後述、#137/#178）→enabled プラグインを store から起動（起動スペック組み立てとシークレット解決は core の `plugins::spec::plugin_spec` 呼び出し、F-58/64/65、#217）→起動時回復（§5.3、再開不能タスクは `task retry/cancel` を案内）→孤児 worktree 警告（F-24）→[orchestrator-core の run Engine](/components/orchestrator-core.md) に委譲。終了時に summary（fetched/ingested/dispatched/done/failed と waiting/pending/queued の残タスク）を表示。SIGINT / SIGTERM / SIGHUP はどれも graceful（実行中タスクは状態DBに残し次回回復、#753）。ハンドラは `run.lock` 取得直後に `stop_requested` で登録するので、起動中に届いた停止も既定動作の即死にならず保持され、Engine は初回 cycle の前にそれを見て dispatch せずに止まる。非 unix ビルドは `ctrl_c()` のみ。**#462: `--json` で summary を `RunSummary` の JSON ドキュメント 1 件として stdout に出す**（散文の代わり。`stats` / `waiting` / `pending` / `queued` / `interrupted`）。`run` の stdout への書き込みは `print_summary` と dry-run の 1 行だけで、config error/warning・hook token 助言・回復の要確認はすべて stderr、core ライブラリとプラグインは直接出力を持たない（すべて tracing 経由）ため、「stdout はパース可能な出力だけ」の契約は構造的に保たれる。**`--dry-run` とは `conflicts_with` で排他**（exit 2）— push 型ソースにはプレビュー対象が無く、`DryRunEntry` の生成箇所は 0 件なので、JSON にしても空配列を返して「プレビューできない」と言い直すだけになる。**終了コードは summary から導出しない**: 失敗タスクを正しく記録した run は仕事を果たしているので `failed > 0` でも 0 のままで、判定は `--json` を読む呼び出し側に委ねる。
- **#554 の CLI 側の帰結**: `config validate` は online パートで各プラグインの `claimed_options` を集め、`[[workflows]]` のプラグイン定義キーがちょうど 1 つの引き取り手を持つかを検査する（`--offline` はこの検査ができないので、その旨を 1 行出す）。`run` も**プラグイン起動直後に同じ検査**を行い、引き取り手のないキーがあれば起動を止める —— `run` は `config validate` を呼ばないので、片方だけだと「`config validate` を実行しない運用者には何も検出されない」。`doctor` の `projects` チェック（旧 `trackers`、#554 で改名）からは重複検出が消えた（1 リポジトリ → 1 project → 1 source で、書けない状態になったため）。`setup` は `[[projects]]` を 1 件書き、全リポジトリに `project` を紐づける。
- `setup [--plugins <list>] [--secret-backend <backend>] [--dry-run]`（#348/#349、#705 で作り直し。[ADR-0077](/decisions/adr-0077-setup-writes-the-whole-surface.md) が [ADR-0028](/decisions/adr-0028-setup-wizard.md) を置き換えた）: **設定面すべてをコメントで書いた `config.toml` を生成し、その場所と「編集しろ」を案内する**。対話ウィザードではない —— 残る質問は使うプラグインの複数選択 1 問だけで、それが「書かれる内容」ではなく「インストールされるもの」を決める唯一の答えだから残っている。`init` は #705 でこのコマンドに統合され、廃止された。
  - **雛形は `crates/orchestrator-cli/templates/config.toml`**（`include_str!`）。実ファイルなのは検査可能性のためで、詳細と網羅性検査は [config.toml 雛形とその網羅性検査](/development/config-template.md)。生成時に `setup::template` がセクション指令（`# totsuka:section`）で**選んだプラグインの節だけ**に絞り、シークレット指令（`# totsuka:secret <account>`）の次行の参照値を選んだバックエンドの形に書き換える。**指令は生成物に出ない**。
  - **有効になるのは `version = 1` の 1 行だけ**。リポジトリのパス・owner・トークン参照・ワークフローは全てコメント例なので、生成直後に `config validate` が通り、かつ何も動かない。`version` を明示するのは、`#[serde(default)]` が `CURRENT_SCHEMA_VERSION` を返す以上、`version` 無しのファイルが v2 を切った瞬間に黙って v2 として読まれるため（このコマンドからその形は出さない）。
  - **導入したプラグインを `enabled = true` にしない**。`config validate` は enabled なプラグインを実際に起動するので、`[github].token` がコメントのまま有効化すると、セットアップを確認するためのコマンドがそのセットアップ自身で落ちる。
  - **既存 config には足りない節だけを追記する**（既存の行は 1 バイトも変えない）。節の同一性は「見出し行が一致する」か「その節が説明するテーブルが**有効行として**存在する」かの 2 通りで判定する。後者が要るのは、生きている `[github]` の下にコメントの `[github]` 解説を足すと 2 つ目の矛盾する定義に読めるため。これが「1 月に github を選んだ人が 3 月に `[notion]` の雛形を docs 抜きで手に入れる」経路であり、書き換えでなく追記なのは**追記先が利用者のシークレット参照を持つファイル**だから。
  - **機密の値を一切扱わない**（ADR-0028 の決定 5 だけは現行でも生きている）。`--secret-backend`（`op` 既定 / `bw` / `keychain` / `cmd` / `env`）で 1 つ選ばせ、参照名は規約値で自動生成し、**その形を config.toml の参照行にも書く** —— 端末の登録コマンドだけ切り替えると `op://` だらけのファイルの上で `security add-generic-password` を案内することになる。参照行の直上には他 4 種の書式を併記するので、乗り換えにドキュメントが要らない。
  - **非対話は `--plugins <csv>`**（`all` / `none` も受ける）。TTY でなく `--plugins` も無ければ **exit 2** —— 既定の選択を置くと選んでいないプラグインが入り、空にすると成功した実行と見分けがつかない。同じ理由で綴り間違い（`--plugins gihub`）も黙って無視せずエラーにする。`--bundled-dir` はテスト用仕掛けなので hidden のまま（[ADR-0018](/decisions/adr-0018-ci-test-time.md)）。回答ファイル（`--answers` / `--save-answers`）と確認プロンプト（`--yes`）は #705 で削除した —— 運ぶべきものが「回答」から「設定ファイルそのもの」に変わり、中間形式が要らなくなった。
  - **プラグインの調達先は 1 度だけ決めて計画に出す**: バイナリの隣に同梱ツリーがあれば bundled（#345）、無くてチェックアウト内ならそこからビルド（#346）、どちらでもなければ**エラーにせず**手で打つコマンドを印字する。`--all` ではなく**選ばれたものを 1 つずつ** install する。
  - **`doctor` は自動実行しない**。生成直後の config は実質空なので「まだ何も設定されていない」を報告するだけになり、案内と重複する。編集した**あと**に回すものとして案内文に含める（`$EDITOR` も起動しない —— 常駐プロセスやパイプ経由の呼び出しを乗っ取るため）。
  - **ピッカーは `dialoguer` の `MultiSelect`**。`inquire` ではなく —— 前者は `console` 経由で端末に触れるのに対し、後者は `crossterm` を丸ごと引く。**この経路は E2E で検証できない**（テストは TTY を持たない）ので、覆えるのは `--plugins` 側だけである。
- `status [--json]`（#64）: タスク/worktree 一覧と orchestrator 生存表示。SQLite 直読でプラグインを起動しない（§5.5）。run.lock の PID 生存確認で「not running (stale lock)」を明示（F-74）。**#407: 動かないタスクの待機理由**を `not starting yet:` ブロック（`--json` では `tasks[].wait_reason = {kind, since, message}`、無い場合はキーごと省略）で出す。`StateDb::open_notes` が返した**記録**を読むだけで検査は再実行しない — status はオペレータのシェルで走るので、`gh` がそこから見えることは Orchestrator から見えることを意味しないため（[ADR-0037](/decisions/adr-0037-task-notes-in-the-event-log.md) D1）。文面は `agent_tools::blocked_reason` が組み立て、#399 の通知と同じ関数を共有する。**#586: 生きている run の縮退**を `degraded:` ブロック（`--json` では `health = [{kind, message}]`、停止中はキーごと省略）で出す。読み出しは `common::live_health` で、`run.lock` が生きていること**と** `health.json` の `pid` が一致することの両方を要求する — 落ちた run が残した文書は存在しないプロセスの話なので、読めば「縮退している」と嘘をつくことになる。加えて**鮮度**を判定し（`RunHealth::is_stale`、既定 120 秒）、古い文書は**捨てずに** `LiveHealth::stale` として運び、`stale_health_message` の 1 行を足す —— 捨てると、ハングして黙った run について「健全」と報告することになるため。`--json` の `health` は `{recorded_at, stale, degraded}` で、読み手が自分で判断できるよう `recorded_at` も出す。
- `menu [--json]`（#585, F-109）: メニューバー向けの表示（[ADR-0065](/decisions/adr-0065-menubar-status.md)）。`status` と同じく SQLite 直読でプラグインを起動しない。**形＝可用性 / 数＝[要対応](/glossary/attention.md)件数**の 2 チャネルで、既定の出力は SwiftBar のプラグイン書式、`--json` は表示モデル（`MenuModel`）そのもの。可用性は `common::lock_status`（`status` と共有 — 「running」の意味が 2 つに割れないため）から取る。
  - **要対応の定義はこのモジュールの `classify` 一箇所**にあり、`TaskState` を網羅する `match` で書く。`_ =>` を置かないのは、状態が増えたときに黙って「対象外」へ倒れず**コンパイルが通らなくなる**ようにするため。
  - **SwiftBar 書式のエスケープは #280 と同じクラスの防御**である（タイトルはソース由来）。**SwiftBar が読む構文は 3 層**で、`text | key=value` の `|`、**行テキスト内のバックスラッシュエスケープ**（2.1.1 実測）、**`:name:` の SF Symbol / 絵文字展開**（`symbolize` / `emojize` が既定 true）。初版は 2 層目を見落として改行を含むタイトルが 1 行を 3 行に割れ、次のレビューで 3 層目が出た（どちらも実機検収で発覚、ユニットテストは全通過）。現在は `safe()` → **バックスラッシュ二重化** → `|` の退避、の 3 段に加え、**外部由来テキストを載せる全行へ `symbolize=false emojize=false`**（3 層目はエスケープで塞げず、パラメータしか無いため）。escape-not-strip を守るので注入テキストは行の**テキスト側**に丸ごと残り、パラメータ側には届かない。`--json` はバイト完全のまま。この防御を jq / シェルへ出さないことが、`menu` がサブコマンドである理由そのもの。
  - **`main::wants_json` に登録しない唯一のコマンド**。`run` が `Err` を返さない設計（下記）なのでエンベロープが発火する余地が無く、登録すると「失敗しうる」という嘘の含意だけが残る。
  - **#586: `Availability::Degraded`（`⚠`）** — 生きている run が仕事を全部はできない状態。`status` と同じ `common::live_health` を読み、理由をドロップダウンの先頭に並べる（タスクが動かない理由がそれであることが多いため、タスク節より上）。**`run.lock` が優先**なので、停止中の run が残した health は `✕` を `⚠` で塗り替えない。理由の文面も core が組み立てたものだが、SwiftBar の行に載る以上タイトルと同じエスケープを通す。
  - **常に exit 0。** 状態 DB 欠如・`SchemaOutdated`・XDG パスの解決失敗は `MenuModel::unavailable` として**メニューの 1 行**になる（`--json` では `error` フィールド）。メニューバーのプラグインが非ゼロ終了すると項目ごと壊れるためで、`focus` が静かに縮退するのと同じ理由。**`config.toml` は読まない**ので、壊れた config は `menu` に影響しない（レビューで「config 不正も 1 行になる」と書いていたのを訂正）。この契約は関数の外側にも及び、`main` は共有の `Cx::resolve` **より前**に `menu` を分岐させる — 手前の `?` 一つでこのコマンドを非ゼロ終了させられてしまうため。書き込みも `print!` ではなく `write_all` で、`print*!` は書き込み失敗で panic するため（`task export` と同じ教訓。ただし**書き込み失敗を決定的に再現する手段が無く、回帰テストで固定はできていない**）。
  - `bash=` に渡すバイナリは `std::env::current_exe()` の**絶対パス**。**プラグインが走る `PATH` は予測できない**ためで、`totsuka` を名前で呼ぶとターミナルからだけ動いて配布すると壊れる。実測（2026-08-28）では Homebrew と mise shims は入っていたが **`/usr/local/bin` が無かった** —— shims は全ての zsh が読む `.zshenv` 由来、`/usr/local/bin` は login shell でしか走らない `/etc/zprofile` の `path_helper` 由来、という差である。さらに SwiftBar 自身の起動方法にも依存する（`launchctl getenv PATH` が未設定なら launchd 起動のアプリは `/usr/bin:/bin:/usr/sbin:/sbin` だけ）。`current_exe()` はこの問い自体を回避する。

**doctor の非対話ゲート（#289 / #444 / #699、[ADR-0019](/decisions/adr-0019-doctor-onepassword-gating.md)）**: `check_onepassword` と `check_bitwarden` が**最初に**走り、`op --version` / `op whoami` と `bw --version` / `bw status`（いずれもプロンプトを出さない）の結果を `BackendReadiness`（`NotUsed` / `Ready` / `WouldPrompt`）として `SecretReadiness` に載せて後続へ渡す。probe の差分は `BackendProbe` テーブル 1 枚に集約してあり、2 つのバックエンドが同じ 4 分岐を同じ精度で報告することがテストで固定されている（片方だけ雑に測ると、そちらの利用者だけ doctor が弱くなる）。`bw status` は locked でも exit 0 を返すので、判定は JSON の `status` が `unlocked` であること —— パースできない出力は locked 扱い（probe を 1 つ飛ばすより、無人実行がプロンプトで止まる方が高くつく）。ゲート判定は**スキーム非依存**で、各 probe は自分で接頭辞を見ずに `SecretReadiness` に問う: `SecretScheme::of` が参照文字列を `SecretRef` へ parse して分類し（`Silent` = `keychain:` / `${ENV}` / 平文 / 不正参照、`OnePassword`、`Command`、`Bitwarden`）、`skip_for` / `skip_in_toml` / `plugin_secret_skip` が skip 理由（`SecretSkip`: 文面・roll-up 用要約・`{target}` を差し込む次アクション）を返す。**この `match` が `SecretRef` に対して網羅的であることがゲートの担保**で、core にスキームを足すと doctor がコンパイルエラーになる — #444 で `cmd:` を足したとき 3 経路のうち 1 経路にしかゲートを入れておらず、残り 2 経路を後から塞いだ事故の再発を型で止める。readiness を測るかどうかの判定（`scheme_in_use`）は**ディスク上のファイルと実効 config の和**で行う —— `Cx::load_config` は parse の**後**に `TOTSUKA_*` 上書きを適用し、うち `TOTSUKA_LLM_API_KEY_REF` は秘密参照を運ぶので（#785 までは `TOTSUKA_HOOKS_AUTH_TOKEN_REF` もそうだった。hook トークンが `run` の生成するファイルになり廃止）、ファイルだけを見ると上書き経由の `op://` が `NotUsed` と判定されてゲートが開いてしまう。`WouldPrompt`（`op` が無い・セッション無し）や `cmd:` のとき、実解決を要する probe — `plugin:{name}`（`plugin_spec` が `[<name>]` の全文字列 leaf と task_source の `[llm].api_key_ref` を解決する）、`panes`（プラグイン起動）— は**実行せず `skipped` として報告**する。`llm` は一見報告だけだが**同じくゲート**で、`deferred_note` が `None` を返した参照はその場で実解決される（= 新スキームをここで忘れるとバックエンドが起動して stdin で待つ）。判定は**プラグイン単位**（1 つのプラグインの参照が他を巻き添えにしない）で、kind はマニフェストではなく config のロスターから読む（プラグインに触れる前に決める必要があるため）。`Check` の 4 つ目の重大度 `skipped` は `ok: true`（exit code に影響しない）かつ `skip_serializing_if` なので `--json` は後方互換。**セッションがあれば従来どおり全て走る。** **`cmd:` 参照（#444）は同じゲートの無条件版**: セッションに相当する概念が無く、doctor はコマンドが対話プロンプトを出さないことを判別できない（`cmd:op read …` が実在しうる）ため、常に skip する。probe の分岐は `CliProbe`（`Missing` / `VersionFailed` / `Unrunnable` / `Probed`）と純粋関数 `backend_checks`（バックエンドごとの差分は `BackendProbe` テーブルが持つ）に分離してあり、実 `op` / `bw` 非依存でテストできる（この分岐は spawn に埋まっていた間テストが 1 本も無く、#289 の「probe が実装されているのに一度も走っていなかった」事故を許した箇所）。

**外部由来テキストの無害化（#280 / #297）**: `task list` / `task show` / `status` / `logs` / `doctor` の **human 出力**は、第三者が内容を決められるフィールド（`title` / `body` / `author` / `url` / `source_task_id` / `branch` / `worktree_path` / `session_id` / ログの `message`）を `common::safe()` に通してから印字する。制御文字を**除去ではなく可視のエスケープへ**置き換えるため、`ESC[2J` による画面消去も `ESC[1A` による既印字行の上書き（別タスクの state の偽装）も OSC 8 によるリンク偽装も成立しない。**`--json` は通さない** — `serde_json` が既に `\u00xx` へエスケープしており、重ねると二重エスケープで機械可読値が壊れる。`TaskDetail` / `TaskRow` の構築は JSON 分岐より前にあるので、無害化は**分岐より後の print サイトだけ**に置く（構造体側でやると `--json` を巻き込む）。詳細は [端末出力の信頼境界](/security/terminal-output-sanitization.md)。

**#297 で `doctor` を追加**: pane label は `totsuka {source_task_id}`（[ADR-0013](/decisions/adr-0013-orphan-pane-detection.md)）＝外部が決める id を含み、孤児 worktree のパスは title 由来のブランチ名を含む（`render_branch` が畳むのは `Cc` だけで bidi override は素通りする）。`doctor` は障害調査でこそ読まれるコマンドなので出力を信じたい場面で使われる。適用は **`--json` 分岐より後の human レンダリングループ 1 箇所**（`Check` の `name`/`detail`/`action`）と、TTY 時の対話プロンプト（削除/解放の y/N を答える行そのもの）に置く。これにより git の stderr・tmux / プラグインのエラー文が乗る他の `Check` も同時に覆われる。`safe()` の実体は #297 で `orchestrator_core::terminal` へ移り、`common::safe` はその re-export になった（core 自身の stderr ログ層も同じ関数を使うため）。

# フックアセットの書き出し（#137、#178 で core へ移動）

フックスクリプト + workflow 別 settings のレンダリングサブシステム（旧 `src/hooks/`、エピック #131 の描画側）は **#178 で [orchestrator-core](/components/orchestrator-core.md) の `hooks` モジュールへ移動した**（描画・受信・マーカー定数を単一クレートに閉じるため。詳細は core 側の `hooks` 行を参照）。CLI に残るのは薄い呼び出しのみ:

## doctor のフック系プローブ（#141）

`doctor` に**フック機構専用のプローブ**を追加する（既存の `hooks` アセットチェックを複製せず**拡張**する形。既存の `Check::ok`/`Check::fail`「原因 + 次のアクション」パターンに従う）。詳細な切り分け手順は [フックのトラブルシューティング](/operations/hook-troubleshooting.md)。

プローブの実装は `check_*` 関数、`doctor --json` の `.name` に出るチェック名は括弧内:

- `check_hook_socket`（`hook-socket`） — UDS への**自己 POST → 200**（受信サーバ・Bearer・0600 権限の疎通）。トークンは `run` が生成したファイルから `hooks::token::read` で読む（#785 以降 `op://` 等の参照解決が無いので非対話ゲートの対象外）。401 は `run` の起動後にファイルが変わった（消した・作り直した）ことを意味する → `run` を再起動。
- `check_hook_assets`（`hooks`） — スクリプト + `orchestrator-*.json` の存在・**0700/0600 パーミッション**・**内容ハッシュ一致**（既存の `hooks` アセットチェックを拡張。実体は core の `hooks::install` / `hooks::verify_assets` 呼び出し、#178）。
- `check_hook_token`（`hook-token`） — `run` が生成したトークンファイル `$XDG_STATE_HOME/totsuka/hook-token`（#785、[ADR-0099](/decisions/adr-0099-generated-hook-token.md)）を見る。無い → `ok`（初回 `run` 前。`run` が作る）、group/other から読める → `fail`（消して `run` を再起動）、それ以外 → `ok`。**#209 / #214 の「フック対応 agent を使う workflow があるのに `[hooks].auth_token_ref` 未設定なら fail、それ以外は warn」「capability 不明の明示」は #785 で廃止**（利用者が設定するキー自体が無くなったため）。
- `check_hook_deps`（`hook-deps`） — `curl` + `jq` の存在（H-14。無いとフックが送信不能で全て spool 行き）。
- `check_spool`（`hook-spool`） — `spool_dir` の書き込み可否と**バックログ件数**（backlog > 0 は warning、[hook-security](/security/hook-security.md) N-05 の滞留検出）。

## doctor --online: LLM キーのライブプローブ（#267）

`check_llm_key`（`llm`）が答えられるのは「**シークレット参照が解決できるか**」だけで、「**その鍵が API に受理されるか**」ではない。両者は無関係で、実機では `op://` 参照が正しく解決する裏でプロバイダが全リクエストに 401 を返し続けていた。決定の全文は [ADR-0016](/decisions/adr-0016-doctor-online-probe.md)。

- 既定の `doctor` は不変（オフライン・非対話・`op://` を解決しない、[ADR-0006](/decisions/adr-0006-onepassword-secret-backend.md)）。`--online` を明示したときだけ `check_llm_online`（`llm-online`）が走る。
- 実体は core の `gateway_classifier()` で組んだ分類器の **`RepoClassifier::probe`**（#723 までは `OpenAiRouter::probe_auth`）— engine の疎通確認（F-111）と同じ呼び出しで、分類の本経路は通らない。**json_schema を送らず**（構造化出力の受理形はプロバイダ差が大きく、拒否された schema の 400 が「鍵が悪い」に化ける）、**リトライせず**（不調なプロバイダ相手に doctor が固まらない）、`max_tokens: 1`、レスポンス本文は破棄する（2xx = 鍵が受理された、が問い全体）。
- severity は **401/403 のみ `Check::fail`**。タイムアウト・トランスポート・429・5xx は `Check::warn` に留める — ネットワークの不調で exit 3（[ADR-0012](/decisions/adr-0012-cli-exit-codes-json-errors.md)）になると赤信号が「設定が壊れている」の意味を失う。
- オフラインの `llm` が解決に失敗している場合はプローブしない（投げる鍵が無く、同じ失敗を言い直すだけ）。
- **`--online` は `op://` を実際に解決する**ため生体認証プロンプトが出うる。`--help` にも明記しており、CI / cron からは使わない。
- 共通フラグ: `--config <path>`（設定ファイル上書き = F-66 の最上位レイヤ）、`--debug`（**#176: 全コマンドで有効** — `run` 以外は stderr のみの debug 診断（`logging::init_stderr`、ログファイルは作らない）、`run` は従来どおりファイルログのレベルも debug に引き上げ。global フラグが `run` 以外で無視される clig.dev アンチパターンの解消）。`--json` は主要読み取り系コマンド（status / menu / task list / task show / plugin list / doctor）に加え **`run`（#462）** に用意し、宣言は `common::JsonFlag`（`#[command(flatten)]`）で一元化（#177）。`run` だけは読み取り系ではないが、実行結果を呼び出し側が判定できないとパイプラインに組み込めないため例外的に持つ。**`main::wants_json` への登録を忘れると「`--json` を付けたのに失敗時だけ平文 `error:` が出る」非対称になる**ので、フラグ追加とセットで更新すること。**例外は `menu` だけ**で、`Err` を返さない設計（常に exit 0）なので登録する対象が無い。
- **設定ロードの一元化（#208 → #175、[ADR-0009](/decisions/adr-0009-env-override-whitelist.md)）**: `Cx::load_config(&env)` が `config.toml` パース → core の `apply_env_overrides`（F-66 第 2 層 `TOTSUKA_*`）まで行う。**#175 で `plugin` サブコマンド群の独自ローダ（`Locations`）を廃止**し、設定を読むコマンドはすべてここを通る。**片方だけに適用しない**理由は `focus` / `doctor` が `[hooks].socket_path` から `run` のバインドしたソケットを解決するためで、`run` のみだと `TOTSUKA_HOOKS_SOCKET_PATH` 設定時に別のソケットを見る。警告は stderr（`--json` の stdout 契約を壊さない）。CLI フラグ（`--debug`）は**この後**に適用されるため「CLI > env」が適用順で成立する。**設定欠落時のセマンティクスは 2 API で明示的に選ぶ**: `load_config`（欠落 = 「原因 + 次のアクション」エラー。run / config / focus / doctor）と `load_config_or_default`（欠落 = 空設定で続行。plugin install / uninstall / list — `init` 前でも動くべきコマンドのみ。`TOTSUKA_*` レイヤは欠落時も適用されるため、不正なオーバーライド値はファイル有無によらずエラー）。なお `plugin enable`/`disable` は編集対象ファイルの raw テキスト読み（欠落 = エラー）+ `set_plugin_enabled` のまま（コメント・整形を維持し、env レイヤを書き戻さない。宣言済みチェックも同じ raw テキストのパースで行う）。`config show` はファイル内容表示を維持しつつ、有効な env オーバーライドを末尾に一覧表示する（`--redacted` 時は `is_secret_key` で値をマスク）。**#554 で `plugins/*.toml` の走査が消えた** — 表示対象は `config.toml` 1 本だけになった。
- UX 規約（§7）: エラーは「原因 + 次のアクション」（`→` 区切り）。用語は [glossary](/glossary/index.md) に準拠。
- **exit code 体系と機械可読エラー（#177、[ADR-0012](/decisions/adr-0012-cli-exit-codes-json-errors.md) / #755、[ADR-0095](/decisions/adr-0095-run-startup-exit-codes.md)）**: exit code は名前付き定数（`common.rs`）で 6 値 — **0** = 成功 / **1** = 実行時エラー（`EXIT_ERROR`）/ **2** = usage エラー（`EXIT_USAGE`。サブコマンド無し + clap 自身のパース失敗）/ **3** = 診断完走で問題検出（`EXIT_PROBLEMS_FOUND`、現状 `doctor` のみ — 「doctor 自体の失敗 = 1」と区別）/ **4** = `run` の起動時に、人が直すまで再起動しても直らない失敗（`EXIT_CONFIG`。config・機密参照・`env_file`・プラグインの導入不備と `CONFIG_INVALID`）/ **5** = 別の `run` が lock を保持（`EXIT_ALREADY_RUNNING`）。4 / 5 は `run` 専用で、監視する側は再起動しない。分類は `run_cmd` の起動工程の呼び出し元で `ExitWith` に包んで行う（`needs_fix` / `launch_error`）— 同じ型が定常運転中にも出るので `main` の型ダウンキャストでは分けない。特定 code は `ExitWith { code, message }` を `main` が downcast して取り出す。`--json` 指定時のエラーは stderr へ 1 行 compact JSON `{"error":{"message":"<原因>","action":"<次のアクション>"|null}}`（既存文言の最初の ` → ` で分割）、非 `--json` は従来の `error: 原因 → アクション` 平文。stdout の「parseable output, nothing else」契約はエラー時も不変。`focus` は従来どおり常に exit 0（クリック経路を壊さない）。
