# 責務

ユーザー向けの CLI 表面。`clap` でコマンドを解釈し、[orchestrator-core](/components/orchestrator-core.md) のユースケースを呼び出す。

# 公開インターフェース

- bin 名: `totsuka`
- `plugin`（#52）: `install <dir> [--yes] [--enable]` / `install --bundled <name>|--all [--yes] [--enable]` / `uninstall <name>` / `enable <name>` / `disable <name>` / `list [--json]`。install は取得元と SHA-256 を表示し確認を要求（§5.4）、GitHub Release からの取得は v1 未対応（ローカルディレクトリからの install に案内）。
  - **`--bundled`（#345）**: リリース tarball が `totsuka` の隣に置く `plugins/<name>/{<name>, plugin.toml}` からパス指定なしで入れる。探索順は「起動に使われたパスの隣」→「symlink 解決後のパスの隣」の各々について `plugins/` → `../libexec/totsuka/plugins/`（後者は将来の prefix 形式インストール用）。採用したツリーは必ず表示する。**`std::env::current_exe` は macOS で symlink を解決しない**（`_NSGetExecutablePath` は起動に使われたパスを返す。Linux の `/proc/self/exe` とは異なる）ため、`fs::canonicalize` の結果も明示的に探索する — 標準のインストール形（`/usr/local/bin/totsuka` → `/usr/local/lib/totsuka/totsuka` の symlink、プラグインは**リンク先**の隣）はこれが無いと 1 つも見つからない。同梱ツリーが無いのは `cargo install` 由来のビルドでは正常なので、エラー文はディレクトリ install へ案内する。上書き用の `--bundled-dir` は hidden（env 変数を使わないのは、未知の `TOTSUKA_*` が stderr に警告を出し（[ADR-0009](/decisions/adr-0009-env-override-whitelist.md)）stderr を JSON として読む E2E を壊すため）。
  - **`--from-source <name>|--all`（#346）**: totsuka のチェックアウトからビルドして install する開発用の経路。`--repo <dir>` で明示、省略時は cwd から上へ辿って「Cargo ワークスペースのルート**かつ** `plugins/` を持つ」ディレクトリを探す（`git rev-parse --show-toplevel` は**使わない** — 無関係なクローンでも答えてしまい、その後で分かりにくく失敗するため）。`cargo build [--release] -p <pkg>... --bins` を **1 回**だけ起動し（target ディレクトリのロックを 1 度で済ませる。`--bin` を列挙しないのは arch-lint が「プラグイン 1 個 = bin 1 個」を保証しているため）、`prepare_install_from` には manifest として `plugins/<pkg>/plugin.toml` を、バイナリの**ディレクトリ**として `target/<profile>` を渡す（ファイル名 `<name>` は `prepare_install_from` が manifest の `name` から付ける）— **staging ディレクトリを組まない**。`--profile release|dev`（既定 release）、`--print-plan` で cargo を起動せず計画だけ印字。CLI が `cargo` にシェルアウトするのは既に `git` / `op` で行っている作法の範囲内で、`scripts/` に置くとチェックアウトの無い環境で使えず名前→パッケージの対応と config 編集を複製することになるため CLI 側に置いた。
  - **`--enable`**: install と enable の概念分離（F-56）は保ったまま、1 コマンドで両方やるオプトイン。`<dir>` 指定でも `--bundled` でも `--from-source` でも使える。書き込みは `plugin enable` と同じ raw テキスト編集なので、コメント・整形は維持される。**`--enable` 指定時は何も書く前に config.toml の読み取り+パースを preflight する** — 編集はストア更新の後なので、preflight が無いと「インストール済みだがコマンドは失敗」という部分適用が残る。**#175: パス解決・設定ロードは他コマンドと同じ `Cx` 経由**（独自の `Locations` は廃止。`--config` / `TOTSUKA_*` env オーバーライドが plugin コマンドにも効く）。設定欠落時: `install` / `uninstall` / `list` は**空設定で続行**（`Cx::load_config_or_default` — 宣言の照合にしか使わないため `totsuka init` 前でも動く）、`enable` / `disable` は**エラー**（編集対象ファイルが無いため。`→ run totsuka init` を案内）。
- `run [--watch] [--dry-run] [--json]`（#63/#462）: メインループの CLI 表面。設定ロード→`config::validate`（Error があれば起動拒否）→ログ初期化（§5.2）→単一インスタンスロック（F-74、dry-run は読み取り専用のため取得しない）→**フックアセットの書き出し**（core の `hooks::install` 呼び出し、後述、#137/#178）→enabled プラグインを store から起動（起動スペック組み立てとシークレット解決は core の `plugins::spec::plugin_spec` 呼び出し、F-58/64/65、#217）→起動時回復（§5.3、再開不能タスクは `task retry/cancel` を案内）→孤児 worktree 警告（F-24）→[orchestrator-core の run Engine](/components/orchestrator-core.md) に委譲。終了時に summary（fetched/ingested/dispatched/done/failed と waiting/pending/queued の残タスク）を表示。SIGINT は graceful（実行中タスクは状態DBに残し次回回復）。**#462: `--json` で summary を `RunSummary` の JSON ドキュメント 1 件として stdout に出す**（散文の代わり。`stats` / `waiting` / `pending` / `queued` / `interrupted`）。`run` の stdout への書き込みは `print_summary` と dry-run の 1 行だけで、config error/warning・hook token 助言・回復の要確認はすべて stderr、core ライブラリとプラグインは直接出力を持たない（すべて tracing 経由）ため、「stdout はパース可能な出力だけ」の契約は構造的に保たれる。**`--dry-run` とは `conflicts_with` で排他**（exit 2）— push 型ソースにはプレビュー対象が無く、`DryRunEntry` の生成箇所は 0 件なので、JSON にしても空配列を返して「プレビューできない」と言い直すだけになる。**終了コードは summary から導出しない**: 失敗タスクを正しく記録した run は仕事を果たしているので `failed > 0` でも 0 のままで、判定は `--json` を読む呼び出し側に委ねる。
- `init`（#64）: config.toml 雛形（コメントアウト済みテンプレート）と XDG ディレクトリの生成 + git バージョン確認。既存ファイルは決して上書きしない。**非対話であることが CI の依存する契約**なので、対話が要る導入は `setup` が引き受ける。ディレクトリ生成は `ensure_dirs` として切り出され `setup` と共有する。
- **#554 の CLI 側の帰結**: `config validate` は online パートで各プラグインの `claimed_options` を集め、`[[workflows]]` のプラグイン定義キーがちょうど 1 つの引き取り手を持つかを検査する（`--offline` はこの検査ができないので、その旨を 1 行出す）。`run` も**プラグイン起動直後に同じ検査**を行い、引き取り手のないキーがあれば起動を止める —— `run` は `config validate` を呼ばないので、片方だけだと「`config validate` を実行しない運用者には何も検出されない」。`doctor` の `projects` チェック（旧 `trackers`、#554 で改名）からは重複検出が消えた（1 リポジトリ → 1 project → 1 source で、書けない状態になったため）。`setup` は `[[projects]]` を 1 件書き、全リポジトリに `project` を紐づける。
- `setup [--dry-run] [--yes] [--save-answers <file>]`（#348/#349、[ADR-0028](/decisions/adr-0028-setup-wizard.md)）: 対話で config.toml を埋める。**interview（純粋・何も書かない）→ 計画印字 → 1 回だけ確認 → apply（各ステップ冪等）** の 2 フェーズで、質問中の Ctrl-C は痕跡を残さず、apply の途中失敗はどこまで適用したかを印字する（原子性ではなく**収束性**を保証 — 再実行で揃う）。config.toml は `.new` へ書いて `rename`。
  - **レシピ選択 + 穴埋め**: [設定例](/development/config-examples.md) のシナリオを選択肢として提示し、選んだレシピが要求する穴（リポジトリのパス、Slack のメンバー ID、LLM の model）だけを聞く。`trigger` / `mode` / `output` / `verification` はレシピが持つ — この組み合わせこそドキュメントを読まないと答えられない部分で、1 項目ずつ聞いても対話にする意味がない。
  - **Project の Status 列名はレシピが決め打ちしない**（`StatusSlot`）。レシピのワークフロー断片は `{{implement_status}}` のようなプレースホルダを持ち、interview が聞いた答えで `build_config` が置換する。候補は役割を説明する英語名で、**フォールバックではない** — `statuses` を欠く answers ファイルは既定で埋めずに、足すべきキー名を名指しして拒否する（`MissingStatus`）。選んでいない列名を黙って書けば、まさにこの変更が消そうとしている無言の失敗を replay 経路に残すことになる。宣言していないキーも `UnknownStatus` で拒否する（`deny_unknown_fields` は map の中を見ないため）。**`ANSWERS_VERSION` は 2 のまま** — 版が守るのは「古いファイルが違う意味になる」変更で、読むのを拒否するのは厳しくするだけであって意味を変えない。宣言の無いプレースホルダと、使われないスロットは**双方向の整合テスト**が弾く — 前者は利用者の config に literal `{{foo}}` が届き、後者は答えが黙って捨てられる。置換後の trigger は計画の確認画面に出す（列名の誤りは `run` が無言・`doctor` が緑という形でしか現れないため）
  - **既存はスキップ**（上書きも差分マージもしない）。**唯一の例外が `init` の吐いた「全行コメント」の雛形**で、これを未設定扱いにしないと、ドキュメントどおり `init` を先に打った人は `setup` が永久に何もしない。**#554 で単位がファイルからテーブルへ変わった** — プラグイン個別設定が `config.toml` の `[<name>]` へ移ったので、「ファイルが在れば触らない」をそのまま訳すと `config.toml` は setup 自身が書くファイルである以上、2 回目以降にプラグイン設定を 1 つも足せなくなる。`[<name>]` が無ければ**追記**、あれば skip。追記はテキストの末尾へ行い（既に在るテーブルは skip するので二重定義は起こらない）、コメントを含む他の行はバイト同一のまま残る。代償は爆風範囲で、編集をしくじると `config.toml` 全体を損なう —— 以前はプラグイン 1 ファイルで済んだ。
  - **機密の値を一切扱わない**。バックエンド（Keychain / 1Password / env）を一度だけ選ばせ、参照名は規約値で自動生成し、登録コマンドのチェックリストを印字する。実体の検証は `doctor` に委ねる。**`setup` が回答ファイルにトークンを書かないのはこの帰結**であり、dotfiles 運用の安全性はここから出ている。ただしこれは**書き手の性質であって形式の性質ではない**（#466）— 既知のキーは自由文字列なので、手編集したファイルには何でも入りうる。`deny_unknown_fields` が禁じるのは未知のキーだけである。
  - **非対話は `--answers <file>` のみ**。TTY でなく `--answers` も無ければ **exit 2**（パイプから既定値を黙って採用しない）。エラー文は `--answers` を最初に案内する — `init` は全行コメントの雛形しか書かないので、端末なしで動く config が欲しい呼び出し側にとっては答えではなく代替でしかない。**#466 で hidden を外した**: `--save-answers` と対で「1 度答えてファイルを持ち歩き、次のマシンをそこから立てる」経路であり、[setup Playbook](/operations/setup-playbook.md) が dotfiles に置く手順として推奨している。テスト可能性（CLI の E2E は端末を持たない子プロセス）はその帰結であって目的ではない。**hidden のままだったのに Playbook が「hidden フラグなので help に出ない」と釈明を書いていた** — 釈明が要る時点で隠す判断のほうが誤りだった。`--bundled-dir` は本物のテスト用仕掛けなので hidden のまま（[ADR-0018](/decisions/adr-0018-ci-test-time.md)）。
  - **回答ファイルの形式は契約**（#466）。別ビルドが読む前提なので、意味が変わる変更では `ANSWERS_VERSION` を上げ、版違いは**推測せず拒否**する。版は**ファイルの他の部分より先に**読む — 全体をデシリアライズしてからでは、形が変わったフィールドの型エラー（v1 の `recipe = 0` に対する `invalid type: integer`）として出てしまい、利用者に対処のしようがない。`recipe` は `Recipe::key` の**安定キー**であってメニュー位置ではない: 位置だとレシピを 1 つ挿入するだけで既存ファイルが隣のレシピを選び、範囲チェックは通り `version` も動かないので検出できない。キー解決の実装は `recipes::by_key_in(slice, key)` 1 本で、`by_key` は `RECIPES` に対するその別名。パーサは検証用にレシピ集合を注入されるため（並べ替えたリストで「キーが順序を生き延びる」ことをテストで固定している）スライスを取る側が本体になる。対話経路のメニュー選択だけは、その場で `prompt` が返した位置なので添字でよい。
  - 回答ファイルは**レシピが宣言する穴（`github` / `slack_user_id` / `llm`）が埋まっているかも検証する** — 対話経路は穴をそのまま質問するので空きえないが、手書きのファイルは空きうる。素通ししてしまうと `verification = "llm"` かつ `[llm]` 不在の config が生成され、setup は成功と報告して実行時に落ちる。
  - **#349: config を書いて終わりではない**。同一コマンドで続けて (a) プラグイン個別設定の `[<name>]` テーブルを `config.toml` へ追記し（#554 まではファイル `plugins/<name>.toml` の生成だった）、(b) レシピのプラグインを install + enable し、(c) `doctor` をインプロセス実行して **exit 3 を伝播**する。新マシンで打つコマンドが 1 本になるのがこの epic の目的なので、途中で「次はこれを実行」と案内して終わるのは目的を果たさない。
    - **プラグインの調達先は 1 度だけ決めて計画に出す**: バイナリの隣に同梱ツリーがあれば `--bundled`（#345）、無くてチェックアウト内なら `--from-source`（#346）、どちらでもなければ**エラーにせず**実行すべきコマンドを印字する（`cargo install` 由来のビルドでは同梱ゼロが正常）。hidden `--bundled-dir <DIR>` で固定でき、指定時はチェックアウトへフォールバックしない — E2E は端末を持たない子プロセスをこのチェックアウト内で起動するので、固定できないと `cargo build` を踏む（[ADR-0018](/decisions/adr-0018-ci-test-time.md) 違反）。env 変数を使わないのは [ADR-0009](/decisions/adr-0009-env-override-whitelist.md) のため。
    - `--all` ではなく**レシピが挙げたプラグインを 1 つずつ** install する。`--all` だと、たまたま同梱されている他のプラグインまで enable してしまう。
    - **`[<name>]` テーブルには「既定値を持たない必須キー」だけを書く**。`herdr` / `macos` は全フィールドに既定があるのでテーブル自体を作らない（空テーブルは「人が書いて空にした」と区別できず、以後 setup が埋め直さなくなる）。`github` は `github_login` が、`slack` は `app_token` / `user_token` / `target_user_id` が必須で、これが `Blank` として質問になる根拠。**ボードは `[github]` には書かない**（#554）— `owner` / `owner_type` / `project_number` はトップレベルの `[[projects]]` エントリ（`build_config` → `upsert_project`）へ行き、`[[repositories]].project` がそれを指す。**例外は `slack` の `bot_token` 1 つだけ**で、プラグイン的には opt-in（無ければナッジ無し）だが、本人名義の返信は Slack 通知を一切上げないためナッジが無いとフロー全体が気づかれない（[ADR-0021](/decisions/adr-0021-slack-bot-notification-nudge.md)）。レシピが書く以上、未登録だと「ナッジだけ無効」ではなく**プラグインの起動自体が失敗する**ので、シークレットのチェックリストに載せ、各項目が何を可能にするかを併記する。トークンは参照のみ（値は通さない）。生成物は**プラグイン自身のデシリアライザ**（`GithubConfig` / `SlackConfig`）が受理することをテストで固定する — 「TOML としてパースできる」では、キー名を 1 つ間違えても実行時まで露見しない。
    - **既存の `[<name>]` はスキップ**（上の「テーブル単位で追記 / skip」と同じ規則。別ファイルだった頃はここに「雛形の例外は無い」と書いてあったが、テーブルが `config.toml` に同居する以上、雛形判定は `config.toml` について 1 度行われるだけである）。
    - **設定済みマシンでの再実行では config.toml がスキップされ、プラグイン導入と doctor だけが走る**。これが ADR-0028 で `--repair` を作らない根拠。`--enable` による `[plugins.<name>]` の追記は起きる（`plugin install --enable` と同じ編集）。
- `status [--json]`（#64）: タスク/worktree 一覧と orchestrator 生存表示。SQLite 直読でプラグインを起動しない（§5.5）。run.lock の PID 生存確認で「not running (stale lock)」を明示（F-74）。**#407: 動かないタスクの待機理由**を `not starting yet:` ブロック（`--json` では `tasks[].wait_reason = {kind, since, message}`、無い場合はキーごと省略）で出す。`StateDb::open_notes` が返した**記録**を読むだけで検査は再実行しない — status はオペレータのシェルで走るので、`gh` がそこから見えることは Orchestrator から見えることを意味しないため（[ADR-0037](/decisions/adr-0037-task-notes-in-the-event-log.md) D1）。文面は `agent_tools::blocked_reason` が組み立て、#399 の通知と同じ関数を共有する。**#586: 生きている run の縮退**を `degraded:` ブロック（`--json` では `health = [{kind, message}]`、停止中はキーごと省略）で出す。読み出しは `common::live_health` で、`run.lock` が生きていること**と** `health.json` の `pid` が一致することの両方を要求する — 落ちた run が残した文書は存在しないプロセスの話なので、読めば「縮退している」と嘘をつくことになる。
- `menu [--json]`（#585, F-109）: メニューバー向けの表示（[ADR-0065](/decisions/adr-0065-menubar-status.md)）。`status` と同じく SQLite 直読でプラグインを起動しない。**形＝可用性 / 数＝[要対応](/glossary/attention.md)件数**の 2 チャネルで、既定の出力は SwiftBar のプラグイン書式、`--json` は表示モデル（`MenuModel`）そのもの。可用性は `common::lock_status`（`status` と共有 — 「running」の意味が 2 つに割れないため）から取る。
  - **要対応の定義はこのモジュールの `classify` 一箇所**にあり、`TaskState` を網羅する `match` で書く。`_ =>` を置かないのは、状態が増えたときに黙って「対象外」へ倒れず**コンパイルが通らなくなる**ようにするため。
  - **SwiftBar 書式の `|` エスケープは #280 と同じクラスの防御**である（`text | key=value` の `|` がメタ文字で、タイトルはソース由来）。`safe()`（制御文字・改行を可視化）→ `|` を `\u{7c}` へ、の 2 段。escape-not-strip を守るので注入テキストは行の**テキスト側**に丸ごと残り、パラメータ側には届かない。`--json` はバイト完全のまま。この防御を jq / シェルへ出さないことが、`menu` がサブコマンドである理由そのもの。
  - **`main::wants_json` に登録しない唯一のコマンド**。`run` が `Err` を返さない設計（下記）なのでエンベロープが発火する余地が無く、登録すると「失敗しうる」という嘘の含意だけが残る。
  - **#586: `Availability::Degraded`（`⚠`）** — 生きている run が仕事を全部はできない状態。`status` と同じ `common::live_health` を読み、理由をドロップダウンの先頭に並べる（タスクが動かない理由がそれであることが多いため、タスク節より上）。**`run.lock` が優先**なので、停止中の run が残した health は `✕` を `⚠` で塗り替えない。理由の文面も core が組み立てたものだが、SwiftBar の行に載る以上タイトルと同じエスケープを通す。
  - **常に exit 0。** 状態 DB 欠如・`SchemaOutdated`・XDG パスの解決失敗は `MenuModel::unavailable` として**メニューの 1 行**になる（`--json` では `error` フィールド）。メニューバーのプラグインが非ゼロ終了すると項目ごと壊れるためで、`focus` が静かに縮退するのと同じ理由。**`config.toml` は読まない**ので、壊れた config は `menu` に影響しない（レビューで「config 不正も 1 行になる」と書いていたのを訂正）。この契約は関数の外側にも及び、`main` は共有の `Cx::resolve` **より前**に `menu` を分岐させる — 手前の `?` 一つでこのコマンドを非ゼロ終了させられてしまうため。書き込みも `print!` ではなく `write_all` で、`print*!` は書き込み失敗で panic するため（`task export` と同じ教訓。ただし**書き込み失敗を決定的に再現する手段が無く、回帰テストで固定はできていない**）。
  - `bash=` に渡すバイナリは `std::env::current_exe()` の**絶対パス**。GUI 起動のプロセスは `/usr/local/bin` も mise も含まない最小 `PATH` を継承するので、`totsuka` を名前で呼ぶとターミナルからだけ動いて配布すると壊れる。
- `task export [--since <event_id>] [--task <id>] [--no-detail]`（#463）: 監査ログ（`events`）を **NDJSON で stdout へ**流す。`--json` フラグを持たないのは、この出力形式しか無いため（`wants_json` は `Export` を無条件に true にするので、エラーも JSON エンベロープで出る）。core の `StateDb::for_each_exported_event` にコールバックを渡して 1 行ずつ書くので、メモリは出力サイズに比例しない — `detail` は publish 系の遷移で `publish_artifact`（エージェントの端末出力の全量）を運び 1 行が MB 級になりうるため、これは体裁ではなく要件である（実測: 19.8MB の出力でピーク RSS 8.96MB）。**`| head` で閉じられた場合は成功として終える**（Rust は SIGPIPE を無視するので `EPIPE` が書き込みエラーとして表面化する。ここを失敗として報告すると、このコマンドが存在する理由であるパイプラインで使えなくなる。実測: `task export | head -2` は exit 0・stderr 空。**この挙動はテストで固定してある** — 書き込みエラーに文脈を足す程度のごく普通の編集で黙って壊れうるため、パイプバッファ超えの出力を用意して読み手を途中で落とすテストを置き、修正を無効化すると exit 1 になることまで確認済み）。**存在しないタスク id を `--task` に渡すと `not_found` で失敗する**（`show` / `cancel` / `retry` と同じ扱い。空の書き出しは「そのタスクは何もしていない」と読めてしまい、「そのタスクは存在しない」と区別できないため）。一方**使い切った `--since` カーソルは成功して空**を返す — こちらは本物の答えである。詳細は [state.db](/data/state-db.md) の「外への取り出し」。

- `focus <task-id>`（#155, F-94）: 通知クリックの実行先（terminal-notifier `-execute` が呼ぶ）。実行中 Orchestrator の hook/制御 UDS へ [`POST /focus`](/apis/agent-events.md) し、対象タスクの pane を前面化する（pane フォーカスは Orchestrator 所有のプラグイン経由が唯一の整合経路 = session_id 不透明契約 F-37、[ADR-0005](/decisions/adr-0005-click-to-focus.md)）。**縮退は常に静か（exit 0）**: 設定なし・Orchestrator 停止中（socket 無し）・pane 消失はいずれも短い note を出して正常終了する — クリック経路を壊さない（アプリ前面化は `-activate` が別途担う）。socket パス解決は doctor のプローブと共通ヘルパ（`common::hook_socket_path`）。

- `doctor [--json] [--online] [--no-repair]`（#64/#141/#267/#351）: git / config / state DB / **同梱プラグイン（`bundled-plugins`。バイナリの隣に何が同梱されているかを表示。`cargo install` 由来のビルドでは同梱ゼロが正常なので、検出できない場合も含めて重大度は warning 止まり = `ok: true` で終了コード契約 0/1/3 は不変）** / **worktree 配置テンプレート（`worktree-location`。明示された `[worktree].location` と `[[repositories]].worktree_location` の `${ENV}` 展開可否のみを検査。既定値は `Paths` 由来で常に解決するのでスキップ。worktree 作成はディスパッチ時なので、未設定変数を放置すると run は正常起動したまま全タスクが `fail_dispatch` する — `check_spool` と同型の事前検出）** / **hooks（core の `hooks::install` によるアセット書き出し + フック系プローブ一式、後述）** / プラグイン（インストール+ライブ疎通 probe）/ **LLM キー（`llm` = 参照の解決可否のみ。`--online` 時のみ `llm-online` = プロバイダが鍵を受理するかの実測。後述）** / 孤児 worktree（F-24、TTY では対話確認つき掃除提案）/ **孤児 pane（#211、[ADR-0013](/decisions/adr-0013-orphan-pane-detection.md)。`pane_control` 宣言の agent_ide プラグインを launch → protocol 0.2.2 `session/list` → shutdown で列挙し、`classify_orphan_panes`（純関数・ユニットテスト済み）が label の **source task id**（プロトコル `Task.id` = `source_task_id`、DB 行 id ではない）を文字列照合で DB と突き合わせ — 候補 = 「DB 未知」または「一致する全タスクが終端かつ live worktree なし」、非終端と保持中 worktree の pane は除外（複数一致は保守側に倒す）。TTY では 1 件ずつ `session/release`（列挙した label を `expect_label` の同一性ガードに使用）による解放を提案、`--json`/非 TTY は `panes` チェックの fail で検出のみ報告。対象プラグインが無い構成ではチェック自体を出さず、列挙失敗は warning に留める）**。失敗チェックは「原因 + 次のアクション」で報告し **exit 3**（問題検出。doctor 自体の実行失敗 = 1 と区別、#177）で終了。`doctor` は `run` と同じ書き出しを実行するため、フル run なしでフック一式をマテリアライズする手段も兼ねる。

- `completion <shell>`: clap_complete によるシェル補完生成（zsh / bash / fish 等）。

**doctor の非対話ゲート（#289、[ADR-0019](/decisions/adr-0019-doctor-onepassword-gating.md)）**: `check_onepassword` が**最初に**走り、`op whoami`（プロンプトを出さない）の結果を `OpReadiness`（`NotUsed` / `Ready` / `WouldPrompt`）として後続へ渡す。`WouldPrompt`（`op` が無い・セッション無し）のとき、`op://` の実解決を要する probe — `plugin:{name}`（`plugin_spec` が `[<name>]` の全文字列 leaf と task_source の `[llm].api_key_ref` を解決する）、`hook-socket`（`auth_token_ref`）、`panes`（プラグイン起動）— は**実行せず `skipped` として報告**する。判定は**プラグイン単位**（1 つのプラグインの `op://` が他を巻き添えにしない）で、kind はマニフェストではなく config のロスターから読む（プラグインに触れる前に決める必要があるため）。`Check` の 4 つ目の重大度 `skipped` は `ok: true`（exit code に影響しない）かつ `skip_serializing_if` なので `--json` は後方互換。**セッションがあれば従来どおり全て走る。** **`cmd:` 参照（#444）は同じゲートの無条件版**: セッションに相当する概念が無く、doctor はコマンドが対話プロンプトを出さないことを判別できない（`cmd:op read …` が実在しうる）ため、`cmd:` を含むプラグインの probe・`hook-socket`（`auth_token_ref = "cmd:…"`）・`panes` は常に skip し、`hook-token` / `llm` は「未解決のまま ok」を報告する。

**外部由来テキストの無害化（#280 / #297）**: `task list` / `task show` / `status` / `logs` / `doctor` の **human 出力**は、第三者が内容を決められるフィールド（`title` / `body` / `author` / `url` / `source_task_id` / `branch` / `worktree_path` / `session_id` / ログの `message`）を `common::safe()` に通してから印字する。制御文字を**除去ではなく可視のエスケープへ**置き換えるため、`ESC[2J` による画面消去も `ESC[1A` による既印字行の上書き（別タスクの state の偽装）も OSC 8 によるリンク偽装も成立しない。**`--json` は通さない** — `serde_json` が既に `\u00xx` へエスケープしており、重ねると二重エスケープで機械可読値が壊れる。`TaskDetail` / `TaskRow` の構築は JSON 分岐より前にあるので、無害化は**分岐より後の print サイトだけ**に置く（構造体側でやると `--json` を巻き込む）。詳細は [端末出力の信頼境界](/security/terminal-output-sanitization.md)。

**#297 で `doctor` を追加**: pane label は `totsuka {source_task_id}`（[ADR-0013](/decisions/adr-0013-orphan-pane-detection.md)）＝外部が決める id を含み、孤児 worktree のパスは title 由来のブランチ名を含む（`render_branch` が畳むのは `Cc` だけで bidi override は素通りする）。`doctor` は障害調査でこそ読まれるコマンドなので出力を信じたい場面で使われる。適用は **`--json` 分岐より後の human レンダリングループ 1 箇所**（`Check` の `name`/`detail`/`action`）と、TTY 時の対話プロンプト（削除/解放の y/N を答える行そのもの）に置く。これにより git の stderr・tmux / プラグインのエラー文が乗る他の `Check` も同時に覆われる。`safe()` の実体は #297 で `orchestrator_core::terminal` へ移り、`common::safe` はその re-export になった（core 自身の stderr ログ層も同じ関数を使うため）。

# フックアセットの書き出し（#137、#178 で core へ移動）

フックスクリプト + workflow 別 settings のレンダリングサブシステム（旧 `src/hooks/`、エピック #131 の描画側）は **#178 で [orchestrator-core](/components/orchestrator-core.md) の `hooks` モジュールへ移動した**（描画・受信・マーカー定数を単一クレートに閉じるため。詳細は core 側の `hooks` 行を参照）。CLI に残るのは薄い呼び出しのみ:

- `run` / `doctor` 起動時に `orchestrator_core::hooks::install`（スクリプト 0700 + settings 0600 の冪等書き出し）を呼ぶ。
- `run` は `orchestrator_core::hooks::settings_path` で workflow 別 `--settings` パスを引いて `HookRuntime.settings_paths` を組み立てる。
- `doctor` の `check_hook_assets` は `install`（自己修復）→ `verify_assets`（書き込みなし検査）の結果を `Check` へ変換する（後述）。

## doctor のフック系プローブ（#141）

`doctor` に**フック機構専用のプローブ**を追加する（既存の `hooks` アセットチェックを複製せず**拡張**する形。既存の `Check::ok`/`Check::fail`「原因 + 次のアクション」パターンに従う）。詳細な切り分け手順は [フックのトラブルシューティング](/operations/hook-troubleshooting.md)。

プローブの実装は `check_*` 関数、`doctor --json` の `.name` に出るチェック名は括弧内:

- `check_hook_socket`（`hook-socket`） — UDS への**自己 POST → 200**（受信サーバ・Bearer・0600 権限の疎通）。
- `check_hook_assets`（`hooks`） — スクリプト + `orchestrator-*.json` の存在・**0700/0600 パーミッション**・**内容ハッシュ一致**（既存の `hooks` アセットチェックを拡張。実体は core の `hooks::install` / `hooks::verify_assets` 呼び出し、#178）。
- `check_hook_token`（`hook-token`） — `[hooks].auth_token_ref` が解決できる（keychain/env 参照切れの検出）。**#209 で未設定の扱いを条件付きに変更**: `cfg.workflows` の `agent` を静的マニフェストで引き、`Capabilities::hook_completion` を宣言する agent を使う workflow が 1 つでもあれば **`Check::fail`**（該当 workflow / agent 名を detail に列挙）、無ければ従来どおり `Check::warn`。**#214**: agent のマニフェストがパース不能で capability を判定できなかった workflow は「hook 非対応」扱いに沈黙させず、warn の detail に **capability 不明**として明示する（マニフェスト破損だけで fail → warn への静かな格下げが起きないようにするため。破損自体は `config` チェックと `plugin:*` チェックが fail として捕捉する）。doctor で唯一、構成によって severity が変わるチェック。plugin の enabled 状態や参照整合性は既存の validate / `plugin:*` チェックの責務としてここでは重ねない。
- `check_hook_deps`（`hook-deps`） — `curl` + `jq` の存在（H-14。無いとフックが送信不能で全て spool 行き）。
- `check_spool`（`hook-spool`） — `spool_dir` の書き込み可否と**バックログ件数**（backlog > 0 は warning、[hook-security](/security/hook-security.md) N-05 の滞留検出）。

## doctor --online: LLM キーのライブプローブ（#267）

`check_llm_key`（`llm`）が答えられるのは「**シークレット参照が解決できるか**」だけで、「**その鍵が API に受理されるか**」ではない。両者は無関係で、実機では `op://` 参照が正しく解決する裏でプロバイダが全リクエストに 401 を返し続けていた。決定の全文は [ADR-0016](/decisions/adr-0016-doctor-online-probe.md)。

- 既定の `doctor` は不変（オフライン・非対話・`op://` を解決しない、[ADR-0006](/decisions/adr-0006-onepassword-secret-backend.md)）。`--online` を明示したときだけ `check_llm_online`（`llm-online`）が走る。
- 実体は core の **`OpenAiRouter::probe_auth`** — `LlmRouter` の本経路を通さない専用メソッドで、**json_schema を送らず**（構造化出力の受理形はプロバイダ差が大きく、拒否された schema の 400 が「鍵が悪い」に化ける）、**リトライせず**（`max_retries = 0`。不調なプロバイダ相手に doctor が固まらない）、`max_tokens: 1`、レスポンス本文は破棄する（2xx = 鍵が受理された、が問い全体）。
- severity は **401/403 のみ `Check::fail`**。タイムアウト・トランスポート・429・5xx は `Check::warn` に留める — ネットワークの不調で exit 3（[ADR-0012](/decisions/adr-0012-cli-exit-codes-json-errors.md)）になると赤信号が「設定が壊れている」の意味を失う。
- オフラインの `llm` が解決に失敗している場合はプローブしない（投げる鍵が無く、同じ失敗を言い直すだけ）。
- **`--online` は `op://` を実際に解決する**ため生体認証プロンプトが出うる。`--help` にも明記しており、CI / cron からは使わない。
- 共通フラグ: `--config <path>`（設定ファイル上書き = F-66 の最上位レイヤ）、`--debug`（**#176: 全コマンドで有効** — `run` 以外は stderr のみの debug 診断（`logging::init_stderr`、ログファイルは作らない）、`run` は従来どおりファイルログのレベルも debug に引き上げ。global フラグが `run` 以外で無視される clig.dev アンチパターンの解消）。`--json` は主要読み取り系コマンド（status / menu / task list / task show / plugin list / doctor）に加え **`run`（#462）** に用意し、宣言は `common::JsonFlag`（`#[command(flatten)]`）で一元化（#177）。`run` だけは読み取り系ではないが、実行結果を呼び出し側が判定できないとパイプラインに組み込めないため例外的に持つ。**`main::wants_json` への登録を忘れると「`--json` を付けたのに失敗時だけ平文 `error:` が出る」非対称になる**ので、フラグ追加とセットで更新すること。**例外は `menu` だけ**で、`Err` を返さない設計（常に exit 0）なので登録する対象が無い。
- **設定ロードの一元化（#208 → #175、[ADR-0009](/decisions/adr-0009-env-override-whitelist.md)）**: `Cx::load_config(&env)` が `config.toml` パース → core の `apply_env_overrides`（F-66 第 2 層 `TOTSUKA_*`）まで行う。**#175 で `plugin` サブコマンド群の独自ローダ（`Locations`）を廃止**し、設定を読むコマンドはすべてここを通る。**片方だけに適用しない**理由は `focus` / `doctor` が `[hooks].socket_path` から `run` のバインドしたソケットを解決するためで、`run` のみだと `TOTSUKA_HOOKS_SOCKET_PATH` 設定時に別のソケットを見る。警告は stderr（`--json` の stdout 契約を壊さない）。CLI フラグ（`--debug`）は**この後**に適用されるため「CLI > env」が適用順で成立する。**設定欠落時のセマンティクスは 2 API で明示的に選ぶ**: `load_config`（欠落 = 「原因 + 次のアクション」エラー。run / config / focus / doctor）と `load_config_or_default`（欠落 = 空設定で続行。plugin install / uninstall / list — `init` 前でも動くべきコマンドのみ。`TOTSUKA_*` レイヤは欠落時も適用されるため、不正なオーバーライド値はファイル有無によらずエラー）。なお `plugin enable`/`disable` は編集対象ファイルの raw テキスト読み（欠落 = エラー）+ `set_plugin_enabled` のまま（コメント・整形を維持し、env レイヤを書き戻さない。宣言済みチェックも同じ raw テキストのパースで行う）。`config show` はファイル内容表示を維持しつつ、有効な env オーバーライドを末尾に一覧表示する（`--redacted` 時は `is_secret_key` で値をマスク）。**#554 で `plugins/*.toml` の走査が消えた** — 表示対象は `config.toml` 1 本だけになった。
- UX 規約（§7）: エラーは「原因 + 次のアクション」（`→` 区切り）。用語は [glossary](/glossary/index.md) に準拠。
- **exit code 体系と機械可読エラー（#177、[ADR-0012](/decisions/adr-0012-cli-exit-codes-json-errors.md)）**: exit code は名前付き定数（`common.rs`）で 4 値 — **0** = 成功 / **1** = 実行時エラー（`EXIT_ERROR`）/ **2** = usage エラー（`EXIT_USAGE`。サブコマンド無し + clap 自身のパース失敗）/ **3** = 診断完走で問題検出（`EXIT_PROBLEMS_FOUND`、現状 `doctor` のみ — 「doctor 自体の失敗 = 1」と区別）。特定 code は `ExitWith { code, message }` を `main` が downcast して取り出す。`--json` 指定時のエラーは stderr へ 1 行 compact JSON `{"error":{"message":"<原因>","action":"<次のアクション>"|null}}`（既存文言の最初の ` → ` で分割）、非 `--json` は従来の `error: 原因 → アクション` 平文。stdout の「parseable output, nothing else」契約はエラー時も不変。`focus` は従来どおり常に exit 0（クリック経路を壊さない）。
