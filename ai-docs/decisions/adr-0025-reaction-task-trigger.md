# Context

タスクを起こす手段は「自分宛の mention」だけだった。しかし実運用では**自分宛でないメッセージ**——チームの他メンバー同士のやり取り、自分が投稿したメモ——を拾って totsuka に投げたい場面がある。その都度自分宛に mention を打ち直すのは会話に不自然なノイズを足す。

リアクションなら会話を汚さずに「これを見といて」を表現できる。ただしリアクションは **mention と決定的に違う性質**を持つ: **付ける人を選べない**。チャンネルの誰でも、いつでも、任意のメッセージに付けられる。

# Decision

## 1. 本人が付けたときだけ受理する。緩和口は作らない

`reaction_added` の `user` が `target_user_id`（オペレーター自身）と一致する場合**のみ**タスクを起こす。

**他人のリアクションを受理すると、同僚が絵文字を 1 つ付けるだけでオペレーターのマシンにタスクを投げ込める。** worktree が作られ、エージェントが起動し、リポジトリを読み、コマンドを実行する。これは実質的なリモート実行トリガであり、Slack のチャンネルに居るだけで誰でも引ける。

user token での購読では他人が付けたリアクションも同じイベントとして届くので、**フィルタするのはこちら側の責務**である。`reaction_added` の `user` は Slack が発行する識別子でクライアント由来の文字列ではないため、この判定は偽装できない。

**allowlist などの緩和設定は config にも作らない。** 「設定で閉じられるから安全」は、既定値と設定ミスの分だけ弱い。開く必要が生じたらその時点で改めて ADR を書く。

実装上も設定値ではなくコード上の不変条件として書き、ユニットと結合の両方に回帰ガードを置いている（`another_users_reaction_is_never_accepted` / `another_users_reaction_submits_nothing`）。後者はガードを無効化すると落ちることを確認済み。

## 2. user scope の `reactions:read` 1 本で足りる

追加するスコープはこれだけで、可視範囲は現状と同じ「本人が参加しているチャンネル」のまま変わらない。本文の取得は既存の `channels:history` / `groups:history` で足りる。[Slack ユーザートークンの取り扱いポリシー](/security/slack-user-token.md) の前提は変わらない。

**bot scope 版は不採用**（下記）。

## 3. 既定は空 = 無効の opt-in

`trigger_reactions` の既定は `[]`。設定しなければイベントは来ても何も起きない。既存インストールがバージョンを上げただけで挙動が変わることはなく、スコープを足していない環境ではそもそもイベントが届かない。

絵文字名は**コロン無し**で保持する（`reaction_added` の `reaction` フィールドがそう来るため）。設定に `":eyes:"` と書かれても同じ集合に落ちるよう、読み込み時に両端の `:` を剥がす。正規化で空になるエントリと正規化後の重複は `config/validate` で弾く——黙ってトリガ集合が縮み、症状が「リアクションが無反応」ではどのエントリが落ちたか分からないため。

なお 👀 は `eyes`、👁 は `eye` で**別物**。カスタム絵文字の alias は Slack が「実際に押された名前」を返すので、alias を使うなら両方を列挙する必要がある。

## 4. mention パイプラインへ合流させる

取得したメッセージを `Mention` に変換し、既存パイプラインへ合流させる。enrich・リポジトリ解決・承認フローは共有コードのまま、下流にリアクション用の分岐は 1 つも増えない。

`task_id` = `{channel}:{reply_ts}` も変えない。結果として**同じスレッド内の mention とリアクションは同一タスクに合流する**（ADR-0015 の意図どおり: 同じ worktree・同じブランチ・同じエージェントセッション）。dedup も同じセットを共有するので、1 つのメッセージに両方が来ても 1 タスクにしかならない。移行するデータは無い。

**mention 判定表とは 1 点だけ意味論が逆になる。** 判定表の 2 行目は「送信者が本人なら無視」（承認済み自動返信でループしないため）だが、リアクション経路は**反応先の投稿者を見ない**。自分の投稿に自分で `:eyes:` を付けて自分のメモをタスク化するのは正当なユースケースであり、ここでループは起きない（自動返信にリアクションが付くことはない）。

## 5. 本文は 2 段構えで引き直す

`reaction_added` のペイロードに**メッセージ本文は入っていない**。`item: {type, channel, ts}` から引き直す必要がある。

`conversations.history` を `latest = oldest = ts` / `inclusive` / `limit = 1` で撃ち、空なら `conversations.replies` にフォールバックする。**`conversations.history` は broadcast されていないスレッド内の返信を返さない**ためで、この 2 段目が無いと「スレッド内の発言にリアクションを付けても無反応」という、イベントの取りこぼしにしか見えない壊れ方をする。

取得失敗と未検出はタスク化せず warn ログで捨てる。到達できないメッセージ 1 件でプラグインが落ちる方が事故が大きい。

## 6. dedup は再取得の**後**に記録する

事前チェック（非破壊）で既知の重複を落として往復を節約しつつ、キーを実際に記録するのは変換が成功した後にする。

Socket Mode はエンベロープを**処理前に** ack するので（Slack は 3 秒以内の ack を要求する）、**Slack は再配送しない**。取得前にキーを記録すると、一時的なネットワーク障害やレート制限でトリガが失われ、しかも復旧手段が無くなる: 復旧しようとリアクションを外して付け直しても、dedup キーは `{channel}:{メッセージの ts}` でイベント由来ではないため同じく落ちる。プロセス再起動で LRU が消えるまで復旧不能になる。

# 検討した選択肢

## bot scope 版（`reaction_added` を bot events で受ける）

**不採用。** bot は会話に参加していないチャンネルのリアクションを見られず、bot をチャンネルに招待して回る運用が必要になる。ADR-0021 で bot は通知ナッジ専用と決めた線引きも崩れる。

## `reactions.list` のポーリング

**不採用。** 結局 `reactions:read` が要るのでスコープは減らず、レイテンシとレート制限だけ増える。Socket Mode の常駐接続が既にあるのに別系統のポーラを足す理由がない。

## 他人のリアクションを許可する allowlist 設定

**不採用。** Decision 1 のとおり、リモート実行トリガを他人に開く設定を最初から持たない。

## `reaction_removed` を購読してタスクを取り消す

**不採用。かつ購読自体しない**（受け取って捨てるより購読しない方が明快）。

リアクションを外す = タスク取り消し、という意味論を持たせると、既に走っているエージェントを外部から止める経路が承認フローとは別にもう 1 本できる。停止手段が 2 系統あると、どちらが権威かという問いが常について回る。

## `event_ts` を dedup キーに混ぜて「付け直し = 再実行」にする

**不採用。** `message_key` は `{channel}:{ts}` のままにする。

結果として**リアクションを外して付け直しても再実行されない**（dedup で落ちる。プロセス再起動を挟めば LRU が消えて再実行される）。これは「同じメッセージ = 同じタスク」として意図した挙動である。誤って外して付け直しただけで二重にエージェントが走る方が事故が大きい。

なお Decision 6 により、**取得に失敗した場合は付け直しで再試行できる**——失敗時にキーを消費しないため。「成功したものは再実行しない / 失敗したものは再試行できる」という切り分けになっている。

## 取得失敗をエラーとして扱う

**不採用。** 到達できないメッセージ 1 件でプラグインが落ちると、リアクション 1 個が常駐プロセスを殺せることになる。warn して捨てる。

# Consequences

## 良くなること

- 自分宛でないメッセージを、会話にノイズを足さずタスク化できる
- 自分の投稿したメモを自分でタスク化できる（mention 経路では構造的に不可能だった）
- 同じスレッドの mention とリアクションが 1 つの会話に合流するので、起動手段が増えても [会話の同一性](/glossary/conversation-continuity.md) は保たれる
- 下流に分岐が増えない。リアクション経路の出力は `Mention` そのもの

## 受け入れるコスト・リスク

- **スコープを 1 つ足す = アプリの再インストール**が必要。再インストールすると `xoxp-` と `xoxb-` が**両方**再発行されるので、Keychain の両方を更新する必要がある（#305 で踏んだのと同じ罠）
- リアクション経路のメッセージ本文には `<@target_user_id>` タグが含まれない。タグの存在を前提にした下流処理があれば経路を分ける必要がある
- `reactions:read` の欠落は「イベントが来ないだけ」でエラーにならず、原因究明が難しい。`auth.test` のレスポンスヘッダから付与スコープを読んで `doctor` で警告する案があるが、現行トランスポートがレスポンスヘッダを読める作りかは未確認で、今回は入れていない
- 本文の再取得で 1〜2 往復増える。mention 経路（本文がイベントに載っている）より起動が遅い
