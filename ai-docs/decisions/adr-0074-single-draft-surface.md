# Status

**採択（stable）。** [ADR-0003](/decisions/adr-0003-slack-reply-assistant.md) の 2 面提示と、[ADR-0021](/decisions/adr-0021-slack-bot-notification-nudge.md) の「記録・監査面は self-DM 記録が担う」という役割分担を**置き換える**。承認フローそのもの（勝手に送信せず、押下時のみ本人名義で送る）は不変である。

# Context

## 実機で出た症状

却下ボタンを押すと、**スレッド内エフェメラルのボタンは消えるのに、DM 側のボタンが消えない**。押し直すとログにこう出る。

```text
INFO task_source_slack::approval: draft already handled
     draft_id="…" action_id="reject_reply" draft.status=Rejected
```

二重送信は防げている。**防げていないのは「もう押す必要がない」ことが画面から分からない**ことで、操作する側からは「却下が不安定」に見える。

## なぜそうなるか

提示面が 2 つあり、**どちらにもボタンがあった**。押下後の後始末は

- 押した面 → `response_url`
- もう一方 → `chat.update`

という**別々の API 呼び出し**で、片方だけ成功しうる。`chat.update` が失敗すれば警告 1 行を残して DM のボタンは live のまま残る。

さらに**二重押下の分岐はボタンを消さない**。`replace_original: false` の通知を出して帰るだけなので、**押しても消えない → また押す**というループになる。

## ゲートウェイ方式で悪化した

`block_actions` は Pub/Sub 経由で **at-least-once** である。`Seen`（上限 1024 の LRU、再起動で消える）を外れた再配送は、**人が 1 回しか押していなくても**二重押下の分岐に入る。Socket Mode では起きにくく、[ADR-0072](/decisions/adr-0072-slack-event-gateway.md) の経路で初めて表に出た。

# Decision

## 1. 面を 1 つにする —— 自己 DM 記録を廃止

**同期を丁寧にするのではなく、同期が要らない形にする。** 面が 1 つなら、それ自身と食い違うことはできない。

残すのは**スレッド内エフェメラル**のほうである。押下の `response_url` が必ず付いてくるので、後始末が 1 回の API 呼び出しで完結し、失敗しても失敗したことが 1 箇所で分かる。

`Draft.dm_ts` と `SharedState` の自己 DM 保持は削除する。`drafts.json` は `deny_unknown_fields` を持たないので、**既存ファイルは `dm_ts` を無視して読める**（移行作業なし）。

## 2. 押下後はエフェメラルを削除せず置換する

従来は「記録面が ✅/❌ を持つから押した面は消してよい」だった。記録面が無くなった以上、**削除すると却下の痕跡がどこにも残らない**。同じブロック集合のボタンを最終状態に差し替えて、その場に残す。

## 3. 二重押下でも面を塗り直す

`replace_original: true` で最終状態を描く。**2 回目に来たこと自体が「ボタンがまだ出ている」証拠**であり、決着済みの面にボタンを残すことが、この分岐に来る押下を生み続ける。再配送で来た場合も同じ扱いでよい —— 冪等な操作は、見た目も冪等であるべきである。

## 5. `response_url` へ送るブロックからは `markdown` ブロックを外す（Amendment、2026-09-15）

決定 2・3 は「同じブロック集合を置換する」と書いていたが、**そのブロック集合はそのままでは `response_url` を通らない**。

`markdown` ブロック（[ADR-0046](/decisions/adr-0046-slack-markdown-block.md)・#454）は `chat.postMessage` / `chat.postEphemeral` では通るのに、**`response_url` では HTTP 500 で拒否される**。しかも**ボディが空**で、`ok: false` もエラーコードも無い —— 分岐できる情報が何も返らない。

実機で確定させた（2026-09-15、#684 を載せた 0.7.8 上で、同じ下書きのブロックを 2 通り投げる。3 つの下書きで独立に 3 回）:

| 返信文字数 | `markdown` ブロックあり | 同じブロックを `section` に差し替え |
|---|---|---|
| 33 | 638 B → **拒否** | 662 B → **受理** |
| 308 | 1445 B → **拒否** | 1469 B → **受理** |
| 1426 | 3487 B → **拒否** | 3511 B → **受理** |

**3 回とも、通ったほうが payload が大きい**（毎回きっかり 24 バイト差）。payload が 5.5 倍に振れても結果が変わらないので、サイズ上限ではなくブロック型が原因である。確定パス（`draft rejected`）と二重押下パス（`already handled`）の両方で同じだった。

したがって `response_url` 向けのレンダリングだけ、返信文を `section`（clipped mrkdwn）で描く。**失うのは決着済みの面のリッチ表示だけ**である —— その面が書き換わる時点で決定は下っており、承認ならスレッドには本物の `markdown` ブロックで返信が既に投稿されている。少し素っ気ない記録と、**そもそも出ない記録**の差である。

決定 2 が消した「削除すると痕跡が残らない」という問題は、この修正で初めて実際に解決される。#684 の時点では置換が毎回失敗していたので、痕跡も残らず、**ボタンも消えていなかった**。

## 4. bot DM は今のまま（ボタンを付けない）

App の Messages は**通知フィード**であり、ADR-0021 の「ナッジにボタンを付けない／承認後に更新しない」は維持する。ここにボタンを足せば面が再び 2 つになり、この ADR が消した問題がそのまま戻る。

# Consequences

## 失うもの

**永続的な記録・監査面が無くなる。** エフェメラルは Slack のクライアントをリロードすれば消えるので、**下書きの寿命（24 時間）より先に操作面が消えうる**。

埋まるのは一部だけである。bot DM のナッジは #456 で返信案の本文をブロックとして同梱しているので、**「何を送ろうとしていたか」は残る**。残らないのは**「承認したのか却下したのか」**で、`bot_token` 未設定ならナッジ自体が無い。

これは意図した取引である —— 2 面あることの代償（片方だけ live に残るボタン）は毎回効き、記録面の価値は後から見返すときにだけ効く。**毎回効くほうを優先した。**

## アップグレード時の過渡状態

**移行作業は要らないが、上げた瞬間に `Pending` のまま残っている下書きが 1 種類だけある。** 旧版が投稿した self-DM 記録はボタンを持ったまま Slack に残り、新版はその面を知らない（`dm_ts` は読み捨てられる）ので、スレッド側で押しても DM 側は live のままになる。

**放置してよい。** その DM のボタンを 1 回押せば、上の「二重押下でも塗り直す」に落ちて最終状態に置き換わる —— **押せば自分で治る**。窓は下書きの寿命（24 時間）で閉じる。移行コードを書く価値のある持続時間ではない。

## `response_url` が通らない配送

決定 5 のとおり、**`response_url` はこちらが送れるブロックを選ぶ**。`markdown` ブロックを含む payload は 500 で全体が落ち、面は 1 ミリも書き換わらない。押下の後始末が `response_url` 1 本に集約された以上、**この面に送る payload の制約は、押下の後始末そのものの制約**である。

空ボディの 500 はコードで見分けられないので、防ぎ方は「送らない」しかない。テストが 1 本これを固定している（`response_url_payloads_never_carry_a_markdown_block`）—— 他のテストはトランスポートを偽装しているので、これが無いと同じ退行が本番まで素通りする。

## `response_url` が無い配送

`GatewayRecord.response_url` は `Option` で、**それが無い `block_actions` は契約上あり得る**（Slack はメッセージのボタンには必ず付けるが、型がそう言っていない）。その場合、下書きは決着するのに**ボタンを消す手段が無い** —— 記録面が無くなった以上、他に直す面もない。

**それでも決着させる。** 操作した人は決めており、承認ならその時点で返信は既に投稿されている。断れば、下された決定を落とすことになる。代わりに**警告を出して黙って成功させない**。二重送信は二重押下ガードが引き続き防ぐので、失われるのは見た目だけである。

## 残すもの

**メンション判定 ③（自己 DM チャンネルを対象外にする）と、そのための `conversations.open` / `im:write` は残す。** 判定 ②（自分の投稿）で実質的に覆えるが、スコープを落とせば**全利用者に再インストールを強いる**（`xoxp-` と `xoxb-` が両方再発行される）。機能的な見返りが無い変更に、その代償は釣り合わない。

コメントは実態に合わせて直す —— `im:write` はもう「下書きを記録するため」ではなく「判定のために自分の DM を特定するため」である。

# 不採用案

- **App の Messages にボタンを移す**: 記録面を保ったまま面を 1 つにできる。ただし `bot_token` が**実質必須**になる（現状は任意で、未設定でも承認フローは完全に動く）。opt-in の機能を必須に昇格させる変更であり、今回の症状を消すために払う対価としては大きい。将来 `bot_token` を必須にする判断を別途するなら、その時に再検討してよい。
- **2 面を残して同期を堅くする**（`chat.update` 失敗時にリトライ、二重押下でも両面を塗り直す）: 症状は軽くなるが、**片方だけ成功しうる構造は残る**。面が 2 つある限り、次の失敗様式が別の形で出る。
