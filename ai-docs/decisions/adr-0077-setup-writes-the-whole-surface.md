# Status

stable。[#705](https://github.com/tomoya-k31/totsuka/issues/705) の実装とともに確定した。
[ADR-0028](/decisions/adr-0028-setup-wizard.md)（対話ウィザード）を**置き換える**ので、あちらは `status: deprecated` にした。

# Context

`totsuka setup` は 4 つの固定レシピで対話し、扱うプラグインは github / slack / herdr / macos の 4 つだった。
notion / discord / orca にはレシピが無く、`[hooks]` / `[tools.*]` / `[log]` / `[llm]` / `[worktree]` の
大半のキーも対話には現れない。**ウィザードで到達できる設定は、設定スキーマのごく一部でしかなかった。**

対になる `totsuka init` も網羅していない。約 70 行のハードコード文字列で、
[設定リファレンス](/development/config-reference.md)（1192 行）が記述するキーのごく一部しか載せていなかった。

結果、利用者は「setup を通したのに、やりたいことの設定方法がどこにも書かれていない」状態に置かれた。

構造的な原因は 2 つある。

1. **対話は網羅に向かない。** 設定パターンが増えるたびに質問か分岐が要り、レシピは組み合わせ爆発する。
   4 レシピで止まっていたのはその帰結である。
2. **雛形の網羅を強制する仕掛けが無い。** キーを増やした PR が雛形を更新しなくても、何も落ちない。

# Decision

## 1. 対話を廃止し、生成物を「全設定パターンの注釈付き config.toml」にする

質問して埋めるのをやめ、**設定面すべてをコメントとして書き下ろし、ファイルの場所と「編集しろ」を案内する**。

コメント 1 行のコストは線形で、対話のような天井が無い。ウィザードが持っていた知識
（どの列がどの profile と噛み合うか）は失うのではなく、雛形末尾の**レシピ集**へ移した
——「コメントを外せばそのまま動く」形で 4 パターン載っている。

## 2. 残す対話はプラグインの複数選択 1 問だけ

*書かれる内容*ではなく*インストールされるもの*を決める唯一の答えなので、これだけは聞く。
UI は `dialoguer` の `MultiSelect`（`inquire` ではなく —— 前者は `console` 経由で端末に触れるのに対し、
後者は `crossterm` を丸ごと引く）。

**非対話経路は `--plugins <csv>`**（`all` / `none` も受ける）。TTY が無く `--plugins` も無い場合は
**エラーで停止する**。既定の選択を置くとユーザーが選んでいないプラグインが入り、空にすると
成功した実行と見分けがつかない。同じ理由で、綴り間違い（`--plugins gihub`）も黙って無視せずエラーにする。

## 3. `init` は `setup` に統合して廃止する

対話を外すと両者は「非対話でディレクトリと config.toml を作る」まで同じになる。
コマンドが 2 つ並ぶ理由が無い。

## 4. 選んだプラグインは導入するが、`enabled = true` にはしない

`totsuka config validate` は **enabled なプラグインを実際に起動する**。`[github].token` がまだ
コメントのまま `github` を有効化すると、**セットアップを確認するためのコマンドが、そのセットアップ自身で落ちる**。
ロスターの有効化は利用者がコメントを外して行う。

## 5. 有効行は「利用者の入力が要らないキー」だけ

書き出した直後に `config validate` が通る状態で渡す。実際に有効になるのは `version = 1` の 1 行だけで、
リポジトリのパス・owner・トークン参照・ワークフローは全てコメント例である。

`version` を明示するのは意図的である。現在 `#[serde(default)]` は `CURRENT_SCHEMA_VERSION` を返すので、
`version` 無しの config.toml は v2 を切った瞬間に黙って v2 として読まれる
（[設定リファレンス](/development/config-reference.md)に未解決の課題として明記されている）。
このコマンドからその形のファイルが出ないようにする。

## 6. 既存 config があれば、足りない節だけを追記する

既存の行は 1 バイトも書き換えない。これは「1 月に github を選んだ人が、3 月に notion の
コメント付き雛形を docs を見ずに手に入れる」経路であり、追記であって書き換えでないのは、
**追記先が利用者のシークレット参照を保持しているファイル**だからである。

節が既にあるかは 2 通りで判定する: 見出し行が一致するか（このコマンドが以前書いた場合）、
あるいはその節が説明するテーブルが**有効行として**存在するか（手書きの場合）。後者が要るのは、
生きている `[github]` の下にコメントの `[github]` 解説を足すと、2 つ目の矛盾する定義に読めるため。

## 7. シークレットのバックエンドは `--secret-backend`（既定 `op`）で 1 つに絞る

**`env` の参照は `TOTSUKA_SECRET_` 接頭辞を使う。** `TOTSUKA_*` は設定オーバーライドの名前空間で、
認識できない名前には毎回 warning が出る（`env_overrides`）。素朴に `TOTSUKA_GITHUB_TOKEN` を案内すると、
このツール自身が export させた変数について、利用者に対処しようのない警告を毎回出すことになる。
接頭辞を予約して除外する。

対話を廃止したので「あなたが選んだバックエンドで、あなたのレシピに必要な一覧」は作れない。
代わりにフラグで選ばせ、**選んだ 1 種の形を config.toml の参照行にも書く**。
端末に印字する登録コマンドだけを切り替えると、`op://` だらけのファイルの上で
`security add-generic-password` を案内することになり、何も読まないシークレットを登録させてしまう。

参照行の直上のコメントには他 4 種の書式を併記する。バックエンドを乗り換える人・別マシンへ持ち運ぶ人が、
ファイルだけで済むようにするため。

## 8. 雛形は実ファイルに置き、網羅を双方向に機械検証する

雛形を `crates/orchestrator-cli/templates/config.toml` に置き `include_str!` で焼く。

**Rust には struct のフィールドを列挙する手段が無い。** リフレクションが無く、導出マクロを新設しない
限り、テストは「このキーの一覧」を手で書き写すことになる —— 写した一覧こそが次にズレるものなので、
検査の意味が消える。ソースをテキストとして読めば、その一覧は書き写さずに得られる。
副次的に、キーの過半を決める `plugins/*` へ `orchestrator-cli` が張っている依存は github / slack の
2 本・dev のみで（[依存境界](/architecture/workspace-dependency-rules.md)）、検査のために 7 本ぶん
張ると CLI の dev ビルドに全プラグインが入る。

`scripts/config-template-lint.sh` が `arch-lint.sh` と同じ枠組みでそれを検査する。
検査は**双方向**である —— 片方向（足し忘れのみ）だと、削除・改名されたキーが雛形に残り続け、
そこからコピーした config.toml が `config validate` で落ちる。
詳細は [config.toml 雛形とその網羅性検査](/development/config-template.md)。

## 9. 末尾では案内とシークレット登録コマンドだけを印字し、`doctor` は自動実行しない

書き出した直後の config は実質空（`version` のみ）なので、`doctor` は「まだ何も設定されていない」を
報告するだけになり、案内と重複する。編集した**あと**に回すものとして案内に含める。
`$EDITOR` も起動しない —— 常駐プロセスやパイプ経由の呼び出しを乗っ取るため。

# Consequences

## 良くなること

- 設定面の**全体**が、利用者の手元のファイルに存在する。「できるかどうか」を調べにブラウザへ行かなくてよい
- 設定キーを増やす PR は、雛形を直さない限り CI で落ちる。網羅が規約ではなく検査になった
- レシピが増えても対話が伸びない。コメント 1 行のコストしかかからない
- `setup` / `init` の使い分けが消えた

## 受け入れるコスト・リスク

- **生成直後は何も動かない。** 以前のウィザードは（4 レシピの範囲では）そのまま `run` できる config を
  作った。今は必ず編集が要る。これは意図した交換で、代わりに天井が無くなった
- **config.toml が 470 行になる。** 短いファイルを好む利用者には冗長である。節ごとの見出しと
  1 キー 1 行の要約で読み飛ばせるようにしているが、短さ自体は失われた
- **`dialoguer` がワークスペース初の端末制御依存になる。** Renovate / audit / deny の管理対象が 1 つ増える
- **チェックボックス UI は E2E で検証できない**（テストは TTY を持たない）。`--plugins` 経路は
  E2E が覆うが、ピッカー自体は手で確かめるしかない
- `--answers` / `--save-answers` / `--yes` が消える。回答ファイルを dotfiles に置いて
  横展開していた運用は、`--plugins` + config.toml の共有に変わる

# 不採用案

## 対話を残し、出力だけ全網羅にする

回答した項目を有効行、それ以外をコメントで同居させる案。網羅の穴（notion / discord / orca に
レシピが無い）はコメントで埋まるが、**レシピの組み合わせ爆発は残る**。原因ではなく症状を塞ぐ形になる。

## プラグインが自分の雛形断片を同梱する

`plugin.toml` の隣に `config-template.toml` を置き、`setup` が連結する案。境界を守ったまま
網羅を構造的に保証でき、検査も各プラグインクレート内に置ける（自分の struct が見える）。
**プラグイン未導入時にその節が出ない**のが決め手で不採用 —— 「他に何ができるか」を見せるのが
このファイルの目的なので、導入していないプラグインの節こそ載っていてほしい。

## 新 RPC でプラグインに雛形を問い合わせる

`config/template` を protocol に足す案。SDK 側で導出すればドリフトは原理的に起きないが、
protocol の版上げと全プラグインの改修が要り、`setup` がプロセス起動を伴うようになり、
そして**未導入プラグインは依然として載らない**。

## `ai-docs/development/config-reference.md` を単一ソースに生成する

docs と雛形が永久に一致する。ソースが Rust の型ではなく散文になり、
**docs 自体の網羅漏れは検出できない**ので不採用。今の形はソースが型なので、その漏れが落ちる。
