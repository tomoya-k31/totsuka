# Status

stable。[ADR-0074](/decisions/adr-0074-single-draft-surface.md)（下書きの提示面は 1 つ、決定はナッジ DM に記録してからエフェメラルを消す）の上に、却下時の入力を足す。Event Gateway 経由は [ADR-0112](/decisions/adr-0112-gateway-reject-modal.md) で扱う。

# Context

却下は「この返信案は違う」という情報しか残さない。後から見返して返信の質を上げたいとき、本当に欲しいのは「本来どう返すべきだったか」で、それはその場で運用者の頭にしか無い。

入力の受け方は 3 つ検討した。

| 案 | 採否 | 理由 |
|---|---|---|
| エフェメラルに `input` ブロックを常設 | 不採用 | 承認ボタンの直前に入力欄が並び、承認時に何か書くべきか迷う（実機の見た目で確認） |
| 却下押下でエフェメラルを入力欄に差し替え | 不採用 | 送信ボタンが無く、確定用のボタンを別に置く必要がある。モーダルのほうが UI として自然 |
| **却下押下でモーダルを開く** | 採用 | Submit / Close があり、「やめる」で承認待ちに戻れる |

# Decision

## 1. 却下の押下はモーダルを開くだけで、決定は送信で行う

`reject_reply` の押下に `trigger_id` があれば `views.open` でモーダルを開き、その時点では何も確定しない。モーダルの「却下する」（`view_submission`、`callback_id = reject_reply_modal`）で却下を確定し、「やめる」なら下書きは `Pending` のまま残る。

`view_submission` には押下元の情報が無いので、モーダルの `private_metadata` に下書き ID・スレッド座標・押下の `response_url` を入れて持ち回る。形はボタンの `value`（`{"d","c","ts"}`）に `r` を足しただけで、パースも同じ関数を使う。

## 2. モーダルが開けない押下は、その場で却下する

`trigger_id` は押下から 3 秒で失効する。`views.open` が失敗したとき（期限切れ・権限・ネットワーク）と、押下に `trigger_id` が無いとき（Event Gateway の押下レコードは持たない）は、従来どおりその場で却下にする。**失うのは代わりの返信だけで、却下は失わない。** 運用者が「却下」を押した意図は、入力欄が出なくても変わらないからである。

## 3. 代わりの返信の置き場所

| 置き場所 | 何のため |
|---|---|
| `Draft.alt_reply`（下書きストア） | 押下の重複・再起動を跨いだ状態として。TTL 24h で消える |
| ナッジ DM の判定記録（`chat.update`） | **人間が後から見返す正本。** 却下した返信案の直後に「代わりの返信」を並べる。ナッジが無い構成では、書き換えたエフェメラルに載る |
| `draft rejected` ログ行の `alt_reply` | 下書きストアの TTL を越えて残る機械可読の記録 |

実機（2026-10-03）で、ナッジ DM の判定記録に「代わりの返信」が載ること、チェックを入れた代わりの返信が質問者メンション付きでスレッドに投稿されることを確かめた。

入力は任意で、空欄（空白のみを含む）は「代わりの返信なし」として扱い、空の記録を作らない。長さは 2900 文字までに制限する（見出し込みでナッジ記録の section ブロック 3000 文字に収めるため）。

## 4. スレッドへの送信は既定オフのチェックボックスで選ぶ

モーダルに「代わりの返信をスレッドに送信する（本人名義）」のチェックボックスを置く。既定はオフで、オフなら記録だけ。オンかつ文面があるときは、承認時の返信と同じく質問者への `<@…>` を先頭に付けて `chat.postMessage`（ユーザートークン・`thread_ts = reply_ts`）で投稿する。宛先は下書きに残した送信者 ID（`Draft.sender_id`）から `asker_prefix` で付け直す。**下書き本文の先頭から読み取らない** —— bot が起点の下書き（ADR-0079）には前置が無く、本文の先頭はエージェントが宛てた第三者のメンションでありうるので、読み取ると無関係な人に通知が飛ぶ。

送信は「記録してから選ぶ」の順で、**投稿に失敗しても却下と記録は残す。** 失敗は押下面に別のエフェメラルで知らせ、文面は記録から手で送れる。判定記録の見出しは送信の有無で分ける（「却下しました」／「却下し、代わりの返信を送信しました」）。状態としては `Rejected` のままで、`Draft.alt_reply_sent` で区別する。

二重送信は、決定済みの下書きへの送信が「決定済み」の経路に入ることで防がれる。

## 5. `views.open` はユーザートークンで呼ぶ

ユーザートークンは常に設定されているので、`bot_token` の有無で機能が変わらない。実機で、ユーザートークンでモーダルが開くことを確認した（2026-10-03）。

# Consequences

- 送信を選んだ却下は、承認と違い「スレッドに出た文面は運用者が書いたもの」になる。記録上は `Rejected` なので、承認率の集計に混ざらない
- 却下は 1 クリックから 2 クリック（押下 → 送信）になる。代わりの返信を書かなくても「却下する」の 1 押しが増える
- モーダルを開いたまま承認ボタンを押すと承認が先に確定し、後から届いた送信は「決定済み」の経路で表面の掃除だけをする
- Gateway 経由では totsuka がモーダルを開けない（押下が届くまで最大 20 秒かかり、`trigger_id` の 3 秒に間に合わない）。[ADR-0112](/decisions/adr-0112-gateway-reject-modal.md) でゲートウェイが代わりに開き、送信を中継する
