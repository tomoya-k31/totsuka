# Status

stable。#584（エピック）の設計決定。実装は #585（`totsuka menu`）と #586（`health.json` と `⚠`）の 2 段で、**どちらも実装済み**。

**実機検収は未了**のため `verified` は付けていない。SwiftBar はこの環境にまだ導入されておらず、`|` のエスケープ規則・`terminal=true`・`bash=` の引用規則は実物での確認が残っている。

# Context

`totsuka run --watch` を回している間、**人間が対応しないと永久に止まるタスクに気づく手段が、流れて消える通知しかない**。

3 つが重なって、見落としが起きやすい:

1. 通知（F-90/F-93）は一過性で、しかも配送失敗は `notify delivery failed (ignored, F-93)` で握り潰される設計。**「通知が来ない」は「異常なし」を意味しない**
2. `waiting_input` と `escalated` は**スロットを解放する**（F-45）ので、同時実行数だけ見ていると「枠が空いている＝順調」に見える
3. 気づくには `totsuka status` を能動的に叩くしかない

一方、仕様 §3.2 は `GUI / Web ダッシュボード` を非目標に挙げ、§7 は「GUI なし」と書いていた。ただし F-94 click-to-focus は既に `terminal-notifier` で GUI 前面化を扱い `-activate <bundle-id>` まで触っているので、**実態は「totsuka 自身は GUI を描かないが、OS の GUI 面には出る」**だった。

# Decision

## 1. 2 チャネル — 形が可用性、数が要対応

メニューバー項目は 1 文字ではなく、グリフとその隣のテキストという **2 チャネル**を持つ。厳密な優先順の階段（要対応 > 異常 > 稼働中 > アイドル）にすると、「止まっていて、かつ 3 件放置されている」ときに片方が消える。両者は直交する事実なので、直交したまま出す。

| チャネル | 意味 |
|---|---|
| 形 | 可用性。`○` = `run` が生きている / `✕` = 停止・stale lock（#586 で `⚠` = 縮退中が入る） |
| 数 | [要対応](/glossary/attention.md)件数。0 件なら数字そのものを出さない |

## 2. 要対応から終端状態を外す

`StateDb::list_tasks` は絞り込みも上限も無く**過去の全タスク**を返す。`failed` / `skipped` を数えると、バッジは**単調増加して二度と 0 に戻らない** —— 「押せば減る」性質を失った数字は数週間で読まれなくなる。定義と根拠は [要対応](/glossary/attention.md)。

「直近 N 時間以内に終わったものだけ数える」案も検討したが、N を決める必要が出るうえ、**見ていないのに消える**という逆の欠陥を持つ。

## 3. 押せるのは focus と読み取りだけ

タスク行のクリックは `totsuka focus <id>` のみ。`totsuka focus` は**常に exit 0 で静かに縮退する**設計（通知のクリック先として作られている）なので、`run` 停止中でも pane 消失でも安全に置ける。

`totsuka task verify --pass` は置かない。押した瞬間に `finalize_success` → 出力ポリシー（PR 作成 / Slack 本人名義返信 / ソース書き戻し）が走り、取り消せない。[エフェメラル承認フロー](/glossary/ephemeral-approval.md)が「勝手に送信しないための防波堤」として作られているのに、メニューバーの 1 クリックがその横に別経路を開けることになる。

## 4. 表示モデル + シリアライザ、整形は Rust 側

`MenuModel`（どの行を・どの節に・どの順で）が本体で、SwiftBar の行書式はその 1 つのシリアライズ。`--json` は表示モデルそのものを返す。

**整形を Rust に置くことが、この設計の中核である。** SwiftBar の行書式は `text | key=value …` で `|` がメタ文字であり、タスクのタイトルは Slack に投稿できる人・GitHub issue を立てられる人が書いたテキストである。エスケープしなければ、タイトルに `|` を 1 つ書くだけで行に任意のパラメータ（`bash=` を含む）を足せる。これは #280 で `totsuka status` に `safe()` を入れて塞いだのと**同じクラスの問題**（[terminal-output-sanitization](/security/terminal-output-sanitization.md)）。

エスケープは 2 段で、順序に意味がある:

1. `safe()` が制御文字を可視のエスケープ形へ —— 改行を潰すのはここで、これが無いと 1 行が 2 行に割れる
2. `|` を `\u{7c}` へ

**escape-not-strip** を守る: 注入テキストは消えず、行の**テキスト側**に丸ごと残る。消してしまうと「そこに何かあったこと」が operator から見えなくなる。

`--json` は #280 の規約どおり**バイト完全**のまま。人間向けレンダリングが無害化し、機械向け出力は加工しない。

## 5. 常に exit 0

メニューバーのプラグインが非ゼロ終了すると項目ごと壊れる。状態 DB 欠如・migration 未適用（`SchemaOutdated`）・XDG パスの解決失敗は、すべて**メニューの 1 行**として描く。`--json` でも同じで、`error` フィールドを持つ完全な文書を返す。これは `--json` のエラーエンベロープ規約（stderr + 非ゼロ終了）から外れる唯一の読み取り系コマンドで、外れる理由がこれである。

**この契約は関数の内側だけでは足りない。** レビューで 2 つの反例が見つかった —— 共有の `Cx::resolve` が `menu` へ分岐する前にあり、`print!` は書き込み失敗で panic する。前者は `main` が `menu` を `Cx::resolve` より前に分岐させることで、後者は `write_all` に変えることで塞いだ。なお **`menu` は `config.toml` を読まない**ので、「config 不正も 1 行になる」という当初の記述は実装より強い主張だった（訂正済み）。

## 6. 設置は docs の手順のみ

SwiftBar のプラグインフォルダは初回起動時にユーザーが選ぶもので固定パスが無く、totsuka 側から一意に決められない。フックアセットを自動生成しているのは「無いと完了判定が壊れる」からであって、任意の表示をユーザーのフォルダに書き込むのは同じ基準ではない。

**バイナリは絶対パスで書く。** GUI アプリの `PATH` には `/usr/local/bin` も mise も入っていない（Finder / LaunchAgent 起動のプロセスは最小 `PATH` を継承する）ので、`totsuka` を名前で呼ぶとターミナルからは動いて配布すると壊れる。`menu` 自身も `std::env::current_exe()` から絶対パスを出す。

## 7. 設定テーブルは増やさない

`[macos]` は notifier-macos プラグインの持ち物（[ADR-0058](/decisions/adr-0058-config-ownership-boundary.md)）なので、コアの `menu` がそこにキーを足すと所有権モデルを壊す。`menu` は設定を必要としない —— 「Open logs」は SwiftBar の `terminal=true` に任せ、バイナリの絶対パスは実行時に解決する。

# 却下した案

| 案 | 破れ方 |
|---|---|
| **`run --watch` 自身がメニューバー項目を持つ** | `run` が落ちたら項目ごと消えるので、**`✕`（止まっている）を原理的に表示できない**。可用性を映す主体は `run` とは別プロセスでなければならない |
| **メニューから `totsuka run` を起こせるようにする** | GUI 起動のプロセスは mise の `PATH` も 1Password の CLI セッションも継承しない。`op://` 参照が解決できず、**起動したように見えて全プラグインが落ちている**という最も判別しにくい状態を作る |
| **`doctor` を定期実行して縮退を出す** | enabled なプラグインが 1 つでもあると `plugin:{name}` チェックがプラグインを起動し、`plugin_spec` 経由で `op://` を含むシークレットを**実解決**する。`--online` 無しでも 1Password の生体認証プロンプトが出うる（[運用ガイド](/operations/operations-guide.md)）。数秒おきに叩く常駐プロセスからは呼べない |
| **ログの warn/error 文言をパターンマッチして縮退を判定** | **メッセージは契約ではない。** リファクタで一語変わった瞬間に、黙って「健全」と言い続ける |
| **独立した Swift/AppKit `.app`** | 新言語・`xcodebuild` の CI ジョブ・Developer ID による公証パイプラインがリポジトリに入る。得るものは UI の自由度だけで、要件はそれを必要としない |
| **Rust + objc2 の常駐バイナリ** | ワークスペース内で完結するのは利点だが、objc2 の GUI コードはテストしにくく、LaunchAgent での常駐管理を自前で背負うことになる |
| **`status --json` に要対応と health を足し、整形は jq スクリプト** | 上記 4 の `\|` エスケープを、型もテストも無い場所へ移すことになる |
| **state.db を GUI から直読み** | GUI がスキーマ版数を知ることになり「正」が 2 つに増える。migration のたびに GUI 側も追従が要る |

# Consequences

- 仕様 §3.2 の非目標から `GUI / Web ダッシュボード` が消え、`Web ダッシュボード / クラウド UI` に縮んだ。ローカル GUI ホストへの表示は §3.1 のスコープ内になる。**`常駐デーモン / サーバ運用` の行は維持** —— 常駐するのは SwiftBar で、totsuka はワンショット実行のままである
- `totsuka menu` は SwiftBar 依存のサブコマンドとして CLI の公開面に入る。SwiftBar 以外のホスト（xbar / tmux / Übersicht）が必要になったら `--json` を読ませるか、シリアライザを 1 本足す
- **SwiftBar は新しいサードパーティ依存**である。totsuka 側の必須依存ではなく、この機能を使う人だけが入れる
- 縮退（`⚠`）は #586 で入った。`run` が毎サイクル `health.json` を書き、`status` / `menu` の両方が同じ記録を読む（F-110）。入るのは**毎サイクル問い直せる 4 つ**だけで、`.corrupt` な spool ファイルのように自動回収されないものは意図的に外してある —— 数えると警告が永久に消えず、`⚠` が背景ノイズになるため
