* **Update**: [task-source-slack](/components/task-source-slack.md) の `reply_instructions` が、**`answer` profile にできないことを指示していた**のを直した（#527）。旧文言は「Pull Request を作成した場合は、その URL を返信文に必ず含めてください」と書いていたが、`answer` は `DENY_FILE_EDITS` に加えて **`DENY_SHELL`（Bash 全体）** を拒否されるので PR は作れない。しかも `triage_instructions` にある「リポジトリのコードは変更しないでください」に相当する一文が**無かった** —— 4 原型で最も read-only な profile が、唯一 read-only の明示を持たず、唯一 PR 作成を示唆していた。
* **Update**: これは実機で踏んだ（`/live-e2e` S4）。エージェントは指示どおり実装を試み、境界に阻まれ、指示が要求した PR URL を返せないので `STATUS:FAILED` を返した。結果として**タスクは失敗し、Slack には返信も下書きも 1 つも出なかった** —— 運用者からはメンションが無視されたようにしか見えない。**境界は正しく効いており、壊れていたのはプロンプトのほう**である。新文言が書くのは**成果物の制約だけ**で、ツールの可否は主張しない —— **このキーは `answer` の既定であると同時に、指示文を持たない kind のフォールバック**（`design` 指定の Slack workflow、profile 無しの workflow）でもあり、そちらは `DENY_SHELL` を持たない／deny が 1 つも付かないので、「シェルが使えない」と書くと**今度は逆向きに嘘になる**（レビュー指摘）。実装が要ると分かった場合も試みずに方針だけ返信へ書かせる（実装を別タスクへ回す運用は環境ごとに違うので絵文字名などは書かない）。
