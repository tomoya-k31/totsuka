* **Update**: [task-source-github](/components/task-source-github.md) / [task-source-notion](/components/task-source-notion.md) / [設定リファレンス（config.toml）](/development/config-reference.md) — #548 派生: `[[projects]]` / `[[databases]]` の各要素に **`triage_status`**（任意）を追加した。triage 起票した item / ページに付ける Status を destination の散文へ織り込む — github は `item-list` / `field-list` で id を引いて `item-edit` する**具体的なコマンド列**まで（一発で済む CLI が無く、手順を名指ししないと「やり方が分からなかった」という報告になる）、notion は status 列の説明に「set it to `値`」を添える形。**プロトコル変更なし**（destination は元から散文）。
* **Update**: **既定は「Status なし」のまま**にした。Status の無い item は `project_status` 条件の trigger に一致しない — **全 workflow が status で絞っている構成なら**人間のトリアージがゲートになる（status 条件の無い trigger には一致するので、ゲートの実在は trigger の書き方次第。レビューで「実装より強い主張」と指摘され弱めた）。**`triage_status` に polling trigger と同じ値（例 `Todo`）を書くとこのゲートが消え、起票が即・無人実装に流れる** — 意図してやる分には正しい設定なので validate では弾かず、docs に明記した。notion 側は `property_map.status` 未設定との組だけ `config/validate` エラー（埋める列を名指しできない指示は従えない）。**この検査も `initialize` では走らない**ので、未 validate の設定は起動して status 指示が黙って落ちる — `project_number` の分離と同じで、レビューで「検査より強い主張」と指摘され書き分けた。
