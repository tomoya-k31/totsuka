* **Update**: [ADR-0062](/decisions/adr-0062-status-vocabulary.md)（#575、破壊的）。`[[workflows]]` の `trigger.project_status` と `on_*.set_status` を **両側 `status`** に統一し、`status_map` を github / notion 両方から廃止した。同じ列を指す 2 つのキーが別名だっただけでなく、**値の解釈経路まで違っていた** —— 列の値を名指す 4 キーのうち写像を通るのは `set_status` だけで、同じ文字列が書き込みでは翻訳されて通り、読み取りでは翻訳されず黙って一致しなかった。`status_map` は「運用者が書いた文字列を、運用者が書いた表で、運用者が書いた別の文字列へ変換する」二重間接で（core は `set_status` の値を一切加工せずプラグインへ渡している）、しかも write-back 側にしか効かないので列名変更を 1 箇所で吸収する用も成していなかった。副産物が 2 つある: `status_map` が閉路検査に作っていた盲点（2 つの名前を 1 列へ寄せると閉路が見えない。`column_cycles` の doc が自分で書いていた）が構造的に消え、`status` を第一名にしていた **notion のワークフローが初めて閉路検査の対象になった** —— それまで `trigger_column` は `project_status` しか読まず、notion の閉路は `config validate` を素通りしていた（回帰テストで固定）。あわせて `status` を **`trigger` に住む core 所有のキー**として正式化し、[ADR-0058](/decisions/adr-0058-config-ownership-boundary.md) の「core は trigger の中身を一切解釈しない」をこの 1 点について改訂した（用途は閉路検査の列グラフ 1 つで、文字列比較しかしない。受理するかは各ソースの自由で、状態列を持たない slack は未知キーとして拒否する）。スキーマ `version` は上げない —— #574 の未知キー検査により旧綴りは 3 つとも硬いエラーになる。
