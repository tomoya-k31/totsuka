* **Update**: プラグイン境界に**プラグイン単位の観測性**を入れた（[#497](https://github.com/tomoya-k31/totsuka/issues/497)、[orchestrator-core](/components/orchestrator-core.md)）。それまで観測手段は `plugin = %name` を持つログ **7 箇所**だけで、メトリクスは 1 つも無く、**「どのプラグインのどのメソッドが遅い / 落ちた」を切り分けられなかった**。この機構の支配的な故障モードは沈黙であり、沈黙こそ観測できていなかった。計装点は **`Inner::call_raw` の 1 箇所**で足りる — 全 O→P 呼び出しがここを通る単一の関門なので、13 メソッドをまとめて覆える。出すのは 4 つ: **(1) `plugin_rpc` span**（`plugin` / `method`）と完了時のイベント（`outcome` / `elapsed_ms`）、**(2) メソッド別の呼び出し数・outcome 別内訳・p50/p95**、**(3) P→O 要求の監査ログ**（`task/submit` は `info`、読み取り専用の `task/lookup` は `debug`）、**(4) stderr 転送のレート制限**（10 秒あたり 100 行、超過分は「N 行抑制」に畳む）。**`outcome` を ok/error の 2 値に潰さなかった**のは、運用者が取る行動が違うため — `timeout` は「生きているが遅い」、`crashed` は「もう居ない」、`rpc_error` は「答えたうえで拒否した」で、単一の failure カウントは 3 つとも同じ数字の裏に隠す。`ok` も内訳に含める（失敗数だけでは率として読めない）。**設計上いちばん効いているのは #495 との噛み合わせ**で、再起動は `Plugin` を丸ごと作り直すためカウンタがゼロから始まる — 素朴に実装すると**最もクラッシュしたプラグインが最も呼び出しの少ないプラグインとして見える**という逆立ちが起きる。`install_restarted` が `insert` する**前**に古いインスタンスの stats を回収し（`insert` が drop を起こすので順序が load-bearing）、退役分と現役分をマージして報告する。クラッシュ / 再起動の回数も**プラグイン名で引ける**ようにした（#495 の全体カウンタは総数として残す）— 「何回起きたか」より「どれが起きているか」が知りたい情報である。レイテンシは**直近 256 サンプルのリング**で保持する: `--watch` は何週間も上がり続けるので無制限は取れないし、この数字が答える問いの有効な窓は元々「最近」である。**JSON のフィールド名でそう明示した**（`p95_ms` の doc に「whole run ではない」と書く）。人間向けサマリは**言及に値するプラグインだけ**印字する（健全な run で毎回ゼロの表を出すと読み飛ばす習慣がつく。`--json` は常に全量）。**メトリクスクレートは入れない**（常駐エクスポータの置き場所が無い。出力面は `run --json` と人間向けサマリ）。**`doctor` にも足していない** — #495 と同じ理由で、`doctor` は別プロセスなので稼働中の orchestrator の呼び出し履歴を観測できず、自分の probe の p95 を出しても意味が無い。**stderr の redaction はしない**（ホストはプラグインが何を秘密と考えているか知らないので正しく消せない）。レート制限だけ入れ、「プラグインの stderr は totsuka のログに素通しで入る」ことを作者の責務として明記した。テストは 2 本追加で、**回収を無効化すると `calls` が 2 → 1 に落ちる**（＝リセットされる）ことを実測で確認済み。
