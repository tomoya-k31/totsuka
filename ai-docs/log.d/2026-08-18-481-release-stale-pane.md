* **Fix**: `dispatch_one` が、一度でも dispatch されたタスクの**前回セッションの pane を dispatch 前に `session/release` する**ようにした（[#481](https://github.com/tomoya-k31/totsuka/issues/481)、[orchestrator-core](/components/orchestrator-core.md)、[ADR-0010](/decisions/adr-0010-worktree-cleanup-pane-release.md)）。`totsuka task cancel` は CLI プロセスでプラグインホストを持たないため **DB を書くだけで pane を閉じられない**。閉じるのは `cleanup_worktree` の `release_pane`、つまり `worktree_sweep_interval` の掃引待ちである。その窓の中で `task retry` すると生きた pane の上へ dispatch し、task id から agent 名を導くプラグインが自分自身と衝突する — herdr は `agent_name_taken` を返し、**retry は 0.7 秒で `failed`**（`cancelled → queued → failed`）になり、後続の掃引でも回復しない。実機 E2E（2026-08-17）で踏み、`herdr pane close` してから同じ retry を打つと成功することで原因を確定した。**同じ衝突は retry でなくても到達できる** — worktree 削除より長生きした pane を持つ `done` タスクへの追いメッセージ（#242）。`task/cancel` ではなく `session/release` を選んだのは `expect_cwd` の同一性ガードのため（herdr の pane id は位置ベースで、無防備な close は id が今指している別の pane を巻き込む）。置き場所は `wire_hooks` の**前**でなければならない — 後ろでは `reserve_session` が作った空の新行が `latest_session` になり、生きた pane へ届かない。あわせて dispatch 成功時に `released_panes` からその task を落とす（新しい pane ができた以上、前回の「解放済み」メモは新 pane の解放を抑止する）。**[ADR-0010](/decisions/adr-0010-worktree-cleanup-pane-release.md) の Consequences にあった「Cancelled タスクは `cancel()` が既に pane を閉じている」は誤りだったので訂正した** — 誰も `task/cancel` を呼んでおらず、この一文が 4 週間ぶんの誤った安心を与えていた。回帰テストは `cleanup = manual`（掃引が pane を一切解放しない構成）で張り、release が 2 つの `task/dispatch` の**間**に来ることまで固定した。修正を無効化すると落ちることを確認済み。
