* **Fix**: `dispatch_one` が、一度でも dispatch されたタスクの**前回セッションの pane を dispatch 前に `session/release` する**ようにした（[#481](https://github.com/tomoya-k31/totsuka/issues/481)、[orchestrator-core](/components/orchestrator-core.md)、[ADR-0010](/decisions/adr-0010-worktree-cleanup-pane-release.md)）。`totsuka task cancel` は CLI プロセスでプラグインホストを持たないため **DB を書くだけで pane を閉じられない**。閉じるのは `cleanup_worktree` の `release_pane`、つまり `worktree_sweep_interval` の掃引待ちである。その窓の中で `task retry` すると生きた pane の上へ dispatch し、task id から agent 名を導くプラグインが自分自身と衝突する — herdr は `agent_name_taken` を返し、**retry は 0.7 秒で `failed`**（`cancelled → queued → failed`）になり、後続の掃引でも回復しない。実機 E2E（2026-08-17）で踏み、`herdr pane close` してから同じ retry を打つと成功することで原因を確定した。**retry だけの話ではない**: release が transport エラーで失敗すると `cleanup_worktree` は worktree を削除したうえで `released_panes` に記録しないが、次の掃引は `if !Path::new(path).exists()` で早期 return するので **release は二度と再試行されず pane が恒久的に漏れる**。既定 `manual` の implement タスクはそもそも `Retain` のまま pane が生き続けるので、次の dispatch がそれを閉じないと既定構成で衝突が残る。`task/cancel` ではなく `session/release` を選んだのは `expect_cwd` の同一性ガードのため（herdr の pane id は位置ベースで、無防備な close は id が今指している別の pane を巻き込む）。置き場所は `wire_hooks` の**前**でなければならない — 後ろでは `reserve_session` が作った空の新行が `latest_session` になり、生きた pane へ届かない。あわせて dispatch 成功時に `released_panes` からその task を落とす（新しい pane ができた以上、前回の「解放済み」メモは新 pane の解放を抑止する）。**[ADR-0010](/decisions/adr-0010-worktree-cleanup-pane-release.md) の Consequences にあった「Cancelled タスクは `cancel()` が既に pane を閉じている」は誤りだったので訂正した** — 誰も `task/cancel` を呼んでおらず、この一文が 4 週間ぶんの誤った安心を与えていた。あわせて **[ADR-0010](/decisions/adr-0010-worktree-cleanup-pane-release.md) の決定 1 に例外を書き足した** — `Retain` / `Dirty` は pane を保持するが、**そのタスクをもう一度 dispatch すると決めた**ときだけは保持中の pane も閉じる。回帰テストは 2 本。①`cleanup = manual`（掃引が pane を一切解放しない構成）で、release が 2 つの `task/dispatch` の**間**に来ることを固定。②`released_panes` メモのリセット — 削除が失敗する（worktree を lock した）状況でメモが残ったまま再 dispatch させ、**新しい pane も解放されること**を固定した。②が無いと、新 pane の解放が黙って抑止され、症状は「pane が 1 枚ずつ増える」だけになる（#210 の症状そのもの）。どちらも修正を無効化すると落ちることを確認済み。診断のため dispatch 地点にログを 1 本置いた（閉じたら `info`、RPC 自体が失敗したら `warn`）— `released: false` は「既に消えていた」と「同一性不一致で拒否」を区別できないので、そこは沈黙させ、区別はプラグイン側の warn（中継される）に委ねている。
