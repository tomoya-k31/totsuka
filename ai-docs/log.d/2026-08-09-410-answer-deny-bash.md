* **Creation**: [ADR-0035 answer profile は Bash ごと取り上げ、claude の plan モードを渡さない](/decisions/adr-0035-answer-profile-shell-removal.md)（#410）。実機で deny を全部回り込まれた事象の原因調査つき。残った機構は「ツールごと取り上げること」だけだったので、`answer` の `Bash(...)` パターン列挙を裸の `Bash` 拒否へ置き換える。到達不能になる `DENY_GH_ARTIFACTS` は定数ごと削除（実際より強く読めるリストを残さない）
* **Update**: **`--permission-mode plan` は `Bash` 経由のファイル書き込みを止めない**ことが実測で判明したため、層の表を訂正（`permissionMode` が `plan` のまま `cat >` が成功している。測ったのはこの 1 点で、「plan モードは何もしない」ではない）。シェルを持たないエージェントに対して plan モードが残す実質は `ExitPlanMode` の承認ゲートで、**そのゲートは計画ファイル `~/.claude/plans/<slug>.md` を書く `Write` を我々が消しているせいで無人環境では非決定的に振る舞う**（書けなければ素通り、Bash で迂回して書けたら人間待ちで停止 = #409）。claude の plan フラグは「編集ツールと `Bash` を両方 deny する profile」**かつ**「settings ファイルが渡っている（= deny が実際に届く）」ときだけ落とすことにした。判定は profile 名ではなくルールの中身に対して行う。**両方が要る**のは、deny が `--settings` 経由でしか届かず、そのパスはフック対応 agent にしか解決されないため — profile だけで判定すると orca/mock 系で deny も plan も無い起動になり、変更前より緩くなる。**codex の `--sandbox read-only` は本物のサンドボックスなので対象外** [ADR-0033 D4](/decisions/adr-0033-workflow-profile.md)
