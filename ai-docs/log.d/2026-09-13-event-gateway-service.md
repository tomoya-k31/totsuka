* **Creation**: [slack-event-gateway](/components/slack-event-gateway.md) —— Slack の配信を HTTPS で受け、署名を検証し、本文を保存せずに座標へ射影して Pub/Sub へ publish する常駐しないサービス（#659、[ADR-0072](/decisions/adr-0072-slack-event-gateway.md) 決定 4・6・9・11）。**同一リポジトリの workspace 外**に置いた —— `plugins/` は arch-lint が「totsuka プラグインであること」を要求して置けず、`crates/` に入れると大半の人が一生デプロイしないサービスが全員の `cargo build --workspace` に乗る。代償として totsuka と型を共有できないので、合意は `contracts/slack-event-gateway/` の適合スイートだけになり、**射影は totsuka 側の `gateway_contract::project` とは独立した実装**として書いて、両者が同じ 26 ケースを満たすことで突き合わせる。`--workspace` は除外ディレクトリに届かないため、これが無いと CI が一切かからない —— `ci.yml` に `gateway` ジョブ 1 本（fmt / clippy / test）を足した。**関門は 3 つとも、コンテナの中にしかない。** Slack は IAM プリンシパルになれず、許可リストに使える安定した送信元 IP の一覧も公開していない（推測で組めば配信を落とし始め、それはこの設計が直そうとしている失敗そのものになる）ので、手前に層が無い。①推測不能なパスによるルーティング（登録表の照合は**定数時間で全行を走査**する —— 応答時間から当たった接頭辞を絞られないため）②生のボディに対する HMAC-SHA256 の**定数時間比較**（ボディはパースする前に検証する。再シリアライズしたものを検証すると、署名されていない入力で検査が通る）③タイムスタンプの前後 5 分の窓（署名は「Slack から来たこと」しか証明せず、キャプチャされたリクエストが永久に使えるのを止めるのは窓だけである）。**未登録のパスと署名不正は応答から区別できない** —— 「そのトークンは存在するが署名が違う」と教えると、パスが総当たりする価値のあるものになる。レビューで**署名検証より手前の欠陥を 2 件潰した** —— どちらも `path_token` だけで到達でき、**signing secret が要らない**。①タイムスタンプを素朴に `UNIX_EPOCH + Duration` していたため、20 桁の値（`u64` にはパースが通る）で panic し、接続ごとタスクが落ちて応答が返らなかった。応答を返せない配信は Slack 側で「配信失敗」として累積するので、**関門が落ちた結果として購読の自動無効化に近づく**という最悪の形をしていた。②ボディ上限が `Content-Length` の有無に依存していて、chunked では**集め終えてから長さを測る**形になっていた。上限の目的は「確保させない」ことなので、これは上限ではない。`Limited` でストリームを打ち切る形に直した。**署名検証より手前は、鍵を知らない相手が到達できる場所である**という見方が抜けていた。**200 を返してよいのは publish が受理された後だけ。** 先に返せばイベントは永久に失われ（Slack は 200 を配信成功とみなし再送しない）、逆に失敗を返すのも無料ではない（失敗の累積こそが購読の自動無効化の条件）。メンションでないメッセージにも 200 を返すのはこのためで、非 200 は「配信失敗」として数えられる。**本文を保存しない・外部送信しない・ログに出さない**は、スキーマに本文フィールドが無いこととは**独立に**テストで守る（プロセスは文字列をメモリに保持することも出力することもできるので、スキーマは保証にならない）—— 応答が本文を反映しないことと、publish されたレコードが本文を含まないことを `tests/http.rs` が固定する。依存は短く保った（このコンテナは利用者のクラウドで、その人に見える全メッセージを扱う。crate はそのまま利用者が引き受ける攻撃面になり、distroless なので CVE を当てる先はこの lockfile しかない）—— base64 エンコードと RFC 3339 生成は自前で書き、日付ライブラリも base64 crate も足していない。**Interactivity の Request URL も受ける** —— `application/x-www-form-urlencoded` の `payload` に JSON が入る別形式で、JSON として読むと全押下がパースエラーになり、症状は「ボタンが壊れている」に見える。
