* **Update**: `latest_session` / `list_sessions` の並び順を `created_at` の文字列比較から `id`（rowid）へ変えた（[#478](https://github.com/tomoya-k31/totsuka/issues/478)、[状態DB](/data/state-db.md)、[orchestrator-core](/components/orchestrator-core.md)）。`created_at` は RFC3339 の**文字列**で、`time` の整形が小数部を必要な桁数だけ出すため幅が一定しない（実測で長さ 24〜27 の 4 通り）。先の時刻が後の時刻の**接頭辞**になると次の比較が数字と `Z`（0x5A）になり、**古い行が新しい行より大きい**と判定される（`…10.28357Z` > `…10.283572Z`）。実測で連続 2,000 サンプルの 1,999 ペア中 **278 ペア（約 14%）が反転**していた。`ORDER BY created_at DESC, id DESC` の `id DESC` は**タイブレークなので出番が無い** — `created_at` が（誤って）不一致と判定された時点で決着してしまう。**症状は「再開時に 1 つ前のセッションへ再接続する」**で、テスト `sessions_append_and_latest_wins` が確率的に落ちること（フルラン 4 回中 1 回）としてしか表に出ていなかった。**「フレークなので再実行」で片付けていたら本番バグを見逃していた**。並べ替えに時刻文字列を使っていたのはこの 2 クエリだけで、他はすべて `id` 順（`git grep "ORDER BY"` で確認）。rowid は挿入順に振られ、`delete_session` のロールバック後に再利用される値も生き残っている全行より大きいので、`created_at` が表そうとしていた順序をそのまま表す。`idx_sessions_task` は `(task_id, created_at DESC)` のままにした（1 タスクあたりの行数はリトライ回数程度で、並べ替えのためにスキーマを変える利得が無い）。**回帰テストは注入クロックで `.5Z` と `.53Z` の組を固定して決定的にした** — 14% で落ちるテストではなく、旧 SQL では必ず落ち新 SQL では必ず通るテストにしてある（実際に旧実装へ戻して落ちることを確認した）。
