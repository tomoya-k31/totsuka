* **Update**: [orchestrator-core](/components/orchestrator-core.md) / [運用ガイド](/operations/operations-guide.md) — #542: 各 task_source が `initialize` で申告した claim（protocol 0.5.1）を統合し、`profile = "triage"` の dispatch に**起票先を伝える**ようにした（[ADR-0056](/decisions/adr-0056-multi-tracker-routing.md)）。新設の `plugins::claims::ClaimRegistry` がリポジトリ → 起票先の対応を作る。**core はこの対応表を設定として持たない** — 正本はプラグイン設定で、core は和集合を取るだけである。
* **Update**: **`destination` は `task.instructions` の末尾へ連結する。** 専用チャネルを作らなかったのは、instructions が既に「見えない経路（フックの prompt context）」と「見える経路（invisible injection の無いツール）」の両方を通っているからで、新しい経路を足すと**片方だけ通す穴**を作ることになる。`triage` に限るのは、成果物が**別の場所に置かれる item** である唯一の profile だから — `implement` は渡されたリポジトリの中で作業するので、触る筋合いのないボードの話は誤って行動しうるノイズになる。文面は組み込みの `tracker_destination` テンプレート（`prompts/defaults.toml`）で、**URL を報告に含めることを要求する**。claim の `destination` は機械検査されない散文なので、検収 rubric がそれを判定できるようにするには報告に URL が要る。
* **Update**: **`ClaimRegistry` は dispatch のたびに組み直す。** 起動時に 1 度スナップショットを取ると、プラグイン再起動（#495）が `Plugin` を作り直したあとも**死んだプロセスの claim を語り続ける**。ソースは**名前順**で走査する — `PluginSet::sources` は `HashMap` なので、並べ替えないと重複 claim（設定ミス）が run ごとに違う先へ流れる。
* **Update**: **跨ぎの重複は「報告するが解決しない」。** 各プラグインの `config/validate` は自分のリストしか見ないので、github と notion が同じリポジトリを claim している構成は**両方とも個別には妥当**で、和集合にしか矛盾が現れない。`totsuka run` は起動時 warn、`totsuka doctor` は新設の `trackers` チェックで FAIL にする。ただし `by_repo` には**最初の claim が残る** — 両方落とすと設定ミスが「どこへも流れないタスク」に変わり、実際に設定された 2 箇所のどちらかへ流すより悪い。
* **Update**: `doctor` の `trackers` チェックは `validate_all` が**既に集めた** claim を読む（`ValidatedPlugin` に `claimed_repos` を足した）。claim を集めるにはプラグインを起動する必要があり、**どのプラグインを起動してよいかには実条件が付いている**（`op://` はプロンプトを出しうるので probe しない、`cmd:` はコマンドを実行するので probe しない）。別経路で集めるとその条件を書き写すことになり、ズレたほうが「起動してはいけないものを黙って起動する」側に倒れる。**起動に失敗したプラグインの claim は空になる**が、それは「何も claim しない」とは違うので、1 つでも失敗があれば重複検査自体を skip する（落ちた github プラグインが消えることで重複が「解決」して見えるのを防ぐ）。
