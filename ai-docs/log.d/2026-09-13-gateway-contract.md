* **Update**: [task-source-slack プラグイン](/components/task-source-slack.md) に Event Gateway の契約を凍結した（#656、[ADR-0072](/decisions/adr-0072-slack-event-gateway.md) 決定 4・7）。**イベントゲートウェイは利用者の管理下で動き、フォークして自前実装されることも想定している**（決定 9）ので、totsuka は相手のコードを信用できず、合意できるのはスキーマだけである。しかも決定 4 で publish 対象を絞った結果、**ゲートウェイのフィルタが関門になった** —— 通らなかったメッセージはレコードが存在せず、totsuka から永久に見えない。誤りの重さは非対称で、偽陽性は無駄な `fetch_message` 1 回（`mention.rs` が落とす）だが、偽陰性はメンションが黙って消える。見本 JSON を 1 組置くだけでは形のズレしか捕まらず、「この本文からこのフラグが出るはず」という判定ロジックのズレが通り抜けるため、契約は `contracts/slack-event-gateway/` の**適合テストスイート**（生の Slack ペイロード → 期待される Pub/Sub レコードの組、26 ケース）として置いた。両側の CI がこれを読む。**fixture だけに頼らず、判定の述語そのものを共有した** —— `MentionTags` は `gateway_contract` にあり `mention.rs` のフィルタ表 4 行目がそれを呼ぶ（`extract_subteam_ids` の側は射影専用で、`mention` が使うのは #658 から）。fixture は「誰かが書き留めた形」しか守れないが、コードを共有すれば書き留めなかった形でもずれようがない。`project()` を参照実装の射影として置き、totsuka 側のテストが全ケースに対してこれを回す。スキーマは本文フィールドを持たないが、**それで漏洩が不可能になるわけではない**（差し替えられたゲートウェイはメモリ保持もログ出力も別宛先への送信もできる）ので、その振る舞いはスキーマとは独立に #659 がテストで守る。配送同一性は `kind` ごとに定め、`message` の鍵は `Mention::message_key()` とバイト一致させて既存の重複排除をそのまま効かせた。**`subteam_ids` の抽出は形を検証する** —— `>` まで丸ごと ID とみなすと `<!subteam^S0ABC ここに本文>` で**本文を持たないはずのレコードに本文が乗る**。ただし先頭 `S` や大文字は要求しない（Slack の ID 形式を推測することになり、外すと失われる側に倒れる）。設定キーは `event_source`（既定 `socket`）・`drain_max_age_hours`（既定 24）・`drain_limit`・`watch_poll_interval_secs`（既定 60）を追加し、**`0` を拒否**した（`watch_backfill_max_age_hours = 0` と同じ理由で、「off にしたつもり」が「全部捨てる」になる）。`gateway` 方式の Slack アプリ manifest を `manifest.gateway.yml` として併記し、**Request URL が 2 つ要る**ことを両方の manifest の冒頭に書いた —— Event Subscriptions と Interactivity & Shortcuts は別の設定項目で、Socket Mode ではどちらも同じ WebSocket で届いていたため、片方だけ向けると**メンションは動いたまま承認ボタンだけが一切届かない**。`event_source = "gateway"` は**消費側が無いあいだ拒否する** —— 黙って Socket Mode を動かすのは、このキーが避けようとしている無言の設定ミスそのものだからで、この検査は #657 で消える。消費側（Pub/Sub 取り込み）は #657。
