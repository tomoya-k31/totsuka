* **Creation**: [ADR-0073](/decisions/adr-0073-plugin-config-warnings.md) —— プラグインが「設定は正しいが伝えたいこと」をホストへ渡す口を `ConfigValidateResult.warnings` として足した（protocol 0.7.3、#662）。それまでの選択肢は 2 つしかなく、**どちらも誤りだった**: `errors` は `valid` を false にするので**構築直後のまだ何も受信していない正しい設定を赤くする**（「赤いのが普通」を教えることになり、診断が信用されなくなる）、プラグインの `tracing` ログは `totsuka doctor` が読まないので**知識がそれの最も役に立つ唯一のコマンドに届かない**。加算的・省略可能で `#[serde(default)]` により**不在と空が同じ主張**になるため、既存プラグインは無改修でマニフェストの下限も動かない（`>=0.6.0, <0.8` はそのまま通る）。`doctor` は `Check::warn` として描き `ok: true` のままなので**終了コード契約 0/1/3 は不変**、警告を 1 件も返さないプラグインの出力は 1 バイトも変わらない —— これは #662 の受け入れ条件（Socket Mode の既存利用者の `doctor` が変化しないこと）でもある。分割は `errors` と同じ「原因 → 次のアクション」の形を前提に矢印で行い、**矢印の無い警告も落とさず全文を detail にする**（行を落とすことだけが、不完全に割ることより悪い）。#658 のスコープ警告も将来この口に載せ替えられるが、`check_scopes` はネットワークを使い `config/validate` は意図的にオフラインなので、移すには置き場所の設計がもう 1 つ要る —— 本 ADR では実施していない。
* **Update**: [task-source-slack](/components/task-source-slack.md) と [orchestrator-cli](/components/orchestrator-cli.md) に Gateway 方式の疎通チェックを実装した（#662、[ADR-0072](/decisions/adr-0072-slack-event-gateway.md) の運用面）。**`probe()` の失敗が原因ごとに別のメッセージになった** —— 403 は「identity は通ったが `roles/pubsub.subscriber` が無い」、404 は「名前が違う（`tofu output totsuka_config` が正解を印字する）」、401 は「ADC が受理されない」。ステータスコードという材料は最初から手元にあったのに、1 つの「全部確認しろ」に潰していた。ADC 取得自体の失敗は**再ラップせず素通しする** —— 既に「`gcloud auth application-default login` を実行」という対処を持っており、サブスクリプションの話に包むとそれが埋もれる。**受信履歴を 1 ファイル残すようにした**（`{state_dir}/plugins/{source_name}/gateway-receipt.json`）。これが無いと「一度も受信していない」（= Slack 側の Request URL 未設定という**構築未完**）と「しばらく静か」（= 正常でありうる）が区別できず、動いている設定を何度も疑うことになる。**記録の鍵はフィルタを通ったレコードではなく `pull` が何かを返したこと自体**である —— 答える問いは「Slack からここまでの経路が動くか」で、このビルドが捨てたレコードもそれを同じだけ証明する。`filed` を鍵にすると静かな週を「一度も受信していない」と報告し、正しかった Request URL を再確認させに行くことになる。保存は **Unix 秒**（警告が使うのは「N 日」だけで日付を描かないので、RFC 3339 文字列にすると日付ライブラリを足すか 2 つ目の自前フォーマッタを書くかになる）。記録は全方向で best effort で、書けなくてもドレインループには一切触れない —— 失う診断は警告 1 行、失う可能性のあるものはイベントそのものだからである。[構築手順](/operations/event-gateway-setup.md)に**症状から原因を引く表**を足した。
