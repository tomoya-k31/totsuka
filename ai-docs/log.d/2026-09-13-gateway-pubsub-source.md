* **Update**: [task-source-slack プラグイン](/components/task-source-slack.md) に `event_source = "gateway"` の消費側を足した（#657、[ADR-0072](/decisions/adr-0072-slack-event-gateway.md) 決定 2〜5）。**`socket_mode` と同じ `SocketEvent` を出すので、パイプライン以降は 1 行も変えていない** —— 座標から本文を取り直して Socket Mode が届けるのと同じ `message` イベントの形に組み直し、判定の権威は `mention.rs` に残したままにした。Pub/Sub の取得は REST の `pull` で、**これは long-poll ではない** —— 規定は「メッセージが 1 通以上得られるまで有界時間だけ待つ**ことがある**」なので、待つことは保証されていない。空応答ごとにバックオフを入れないと、サーバが即答した瞬間に busy loop になる。認証は `gcloud auth application-default print-access-token` へのシェルアウトで、[ADR-0006](/decisions/adr-0006-onepassword-secret-backend.md) の 1Password と同じ手口により**新規依存ゼロ**、かつ**サービスアカウントキーを配らずに済む**（各利用者が自分の Google アカウントで自分のサブスクリプションだけを引く）。CLI は**トークンしか出さない**（既定寿命 3600 秒は文書化されているが出力に期限は無い）ので、保守的な TTL で再利用し 401/403 で 1 回だけ破棄して取り直す。**起票窓の判定は `kind` ごとに違う時計で測る。** `record.ts` 一本で測る実装を最初に書いて、テストで落ちて気づいた —— `ts` は「そのレコードが**指している**メッセージ」であり、リアクションやボタン押下では任意に古くなりうる。1 か月前のメモにリアクションしてタスクを起こすのは第一級の使い方だし、下書きのボタンはそのメッセージより長生きする。`ts` で測ると、**誰も問い合わせていないものの古さを理由にそれらを捨てる**ことになる。`message` は `ts`、`block_actions` は `action_ts`（どちらも Slack の時計）、`reaction` は `received_at`（ゲートウェイの時計 —— Slack の `event_ts` は決定 7 が閉じたフィールド列挙に無い）とした。`response_url` の期限切れ判定（30 分）は保持期間とは**別の仕事**で、保持は取りこぼさないため・期限判定は無駄に処理しないためである。**チャンネル監視は `conversations.history` の定期ポーリングに移した**（`watch_poll_interval_secs`、既定 60）—— 起動時バックフィルと同じ関数をタイマーで回すだけで、カーソルを持たないのも同じ理由（重複起票は冪等 ack だが、取りこぼしは黙って消える）。設定は `[slack.gateway]`（`project` / `subscription` / `block_actions_subscription`）で、**#656 の契約には含めていない** —— ゲートウェイはこの名前を見ないので、両側が合意すべきものではない。`app_token` は `gateway` では不要になり、TokenGuard の `apps.connections.open` プローブも `socket` のときだけ走る。レビューで**データロスを 1 件潰した** —— 取得に失敗したレコードも無条件に ack していたため、Slack のレート制限切れや 5xx で**メンションが warn 1 行だけ残して永久に消える**経路があった。`fetch_message` は「見つからない」（`Ok(None)`）と「取得に失敗した」（`Err`）を区別しており、前者は確定的な却下だが後者はインフラ障害なので、後者は ack せず再配送に委ねる。`Seen` への登録も「実際に処理し終えたとき」に限った（先に登録すると、再配送が届いても重複として捨ててしまい、救済のために残した経路が無効になる）。あわせて空振りと失敗を 1 つのカウンタで数えていたのを分けた —— 無風のワークスペースでカウンタが育ち、その後の**1 回目**の一過性エラーがいきなり「持続的障害」の warn を出し、バックオフも初回から上限の 20 秒になっていた（#641 の `eventless_warning` で一度直したのと同型の欠陥である）。起動時のプローブも足した（各サブスクリプションに `pull` を 1 回）—— Socket Mode の `apps.connections.open` と同じ仕事で、ADC の identity 違い・`roles/pubsub.subscriber` の欠落・名前の打ち間違いは、いずれも「`doctor` は緑なのにイベントが来ない」形で失敗する。あわせて [task-source-slack](/components/task-source-slack.md) の `verified` を外した —— 未検証のモジュールを 2 本足した状態で `human:` の検証記録が残ると信頼段階が `human-reviewed` に見えてしまう。**ゲートウェイ障害時の Socket Mode への自動フォールバックは無い** —— Slack アプリ設定上そもそも排他で、切り替えは manifest の変更を伴うため、このプロセスには落ちようがない。
