* **Update**: [task-source-slack プラグイン](/components/task-source-slack.md) に `event_source = "gateway"` の消費側を足した（#657、[ADR-0072](/decisions/adr-0072-slack-event-gateway.md) 決定 2〜5）。**`socket_mode` と同じ `SocketEvent` を出すので、パイプライン以降は 1 行も変えていない** —— 座標から本文を取り直して Socket Mode が届けるのと同じ `message` イベントの形に組み直し、判定の権威は `mention.rs` に残したままにした。Pub/Sub の取得は REST の `pull` で、**これは long-poll ではない** —— 規定は「メッセージが 1 通以上得られるまで有界時間だけ待つ**ことがある**」なので、待つことは保証されていない。空応答ごとにバックオフを入れないと、サーバが即答した瞬間に busy loop になる。認証は `gcloud auth application-default print-access-token` へのシェルアウトで、[ADR-0006](/decisions/adr-0006-onepassword-secret-backend.md) の 1Password と同じ手口により**新規依存ゼロ**、かつ**サービスアカウントキーを配らずに済む**（各利用者が自分の Google アカウントで自分のサブスクリプションだけを引く）。CLI は**トークンしか出さない**（既定寿命 3600 秒は文書化されているが出力に期限は無い）ので、保守的な TTL で再利用し 401/403 で 1 回だけ破棄して取り直す。**起票窓の判定は `kind` ごとに違う時計で測る。** `record.ts` 一本で測る実装を最初に書いて、テストで落ちて気づいた —— `ts` は「そのレコードが**指している**メッセージ」であり、リアクションやボタン押下では任意に古くなりうる。1 か月前のメモにリアクションしてタスクを起こすのは第一級の使い方だし、下書きのボタンはそのメッセージより長生きする。`ts` で測ると、**誰も問い合わせていないものの古さを理由にそれらを捨てる**ことになる。`message` は `ts`、`block_actions` は `action_ts`（どちらも Slack の時計）、`reaction` は `received_at`（ゲートウェイの時計 —— Slack の `event_ts` は決定 7 が閉じたフィールド列挙に無い）とした。`response_url` の期限切れ判定（30 分）は保持期間とは**別の仕事**で、保持は取りこぼさないため・期限判定は無駄に処理しないためである。**チャンネル監視は `conversations.history` の定期ポーリングに移した**（`watch_poll_interval_secs`、既定 60）—— 起動時バックフィルと同じ関数をタイマーで回すだけで、カーソルを持たないのも同じ理由（重複起票は冪等 ack だが、取りこぼしは黙って消える）。設定は `[slack.gateway]`（`project` / `subscription` / `block_actions_subscription`）で、**#656 の契約には含めていない** —— ゲートウェイはこの名前を見ないので、両側が合意すべきものではない。`app_token` は `gateway` では不要になり、TokenGuard の `apps.connections.open` プローブも `socket` のときだけ走る。**ゲートウェイ障害時の Socket Mode への自動フォールバックは無い** —— Slack アプリ設定上そもそも排他で、切り替えは manifest の変更を伴うため、このプロセスには落ちようがない。
