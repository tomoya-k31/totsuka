* **Creation**: [Event Gateway 構築手順](/operations/event-gateway-setup.md) と [Event Gateway（イベントゲートウェイ）](/glossary/event-gateway.md) を新設し、[Slack セットアップ Quickstart](/operations/slack-quickstart.md) に**受信方式の選択**を足した（#663、[ADR-0072](/decisions/adr-0072-slack-event-gateway.md)）。Quickstart はこれまで **Socket Mode を「選ばれた方式」として書いていなかった** —— 唯一の方式として手順に溶け込んでおり、`event_source` に相当する分岐点が文書上に存在しなかった。しかも **Socket Mode と Request URL は Slack アプリ単位で排他**なので、**アプリを作る前に方式を決めないと manifest ごとやり直し**（トークンも全部再発行）になる。分岐を手順 1 の中の枝にするとこの排他性が伝わらないので、**手順 0 として、アプリ作成の手前に置いた**。**1 ページ維持 + GCP 構築だけ別ページ**という構成にしたのは、共通部分（トークン保管・`totsuka setup`・トラブルシューティング）を複製した瞬間に片方だけ古くなるからである。分けた新ページは冒頭で「**Socket Mode で運用するならここから先は一切要らない**」と断り、`allUsers` の組織ポリシー確認（`constraints/run.managed.requireInvokerIam`）を**手順 0 に置いた** —— 通らないと構成そのものを考え直すことになるためである。`min_instance_count = 0` と `max_instances` の上限が費用の前提であることも、調整項目ではないとわかる書き方にした。Quickstart 側は手順 1（どちらの manifest か・App-Level Token と signing secret の使い分け・**Request URL が 2 箇所要る**こと）・手順 2（signing secret は `config.toml` に書かない）・手順 4（`doctor` が見るものの違い）に差分を併記し、トラブルシューティング表に Gateway 固有の 5 行を足した。**そのうち 1 行は「設定を書き換えるだけで方式を切り替えようとした」** —— `event_source` を変えても Slack 側は何も変わらないので、これは実際に踏まれる。生成物は `docs/slack-setup.{md,ja.md}` の再生成と `docs/event-gateway-setup.{md,ja.md}` の新規生成で、手書きの `docs/index.{md,ja.md}` にも行を足した。あわせて `human-docs` スキルの生成マップの表が **Discord の 1 行を落としていた**のを直した（表は写しで正は宣言のほうだが、写しが誤っていると次に読む人が誤る）。
