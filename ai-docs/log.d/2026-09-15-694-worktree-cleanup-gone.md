* **Update**: [orchestrator-core](/components/orchestrator-core.md) — 削除済み worktree のパスに無関係なディレクトリが 1 つあるだけで、掃除ループが 60 秒ごとに `worktree cleanup failed: git status failed: fatal: not a git repository` を出し続ける問題を直した（#694）。タスク行は削除成功後も `worktree_path` を保持する（`set_worktree` に消す口が無い）ので sweep はそのパスを永久に見に来るが、スキップ条件は `Path::exists` だけだったため、跡地にディレクトリが現れると `decide_cleanup` 冒頭の `git status --porcelain` が落ち、**正常終了したタスクについて**プロセスの生きている限り WARN が出続けていた。`decide_cleanup` の先頭に `is_worktree_of`（`repo_path` の `worktree list --porcelain` に当該パスが載っているか）を入れ、載っていなければ `CleanupDecision::Gone`（= `CleanupOutcome::Gone`）として `run::finalize` が debug で抜ける。訊くのは**このリポジトリの registry に属するか**で、「git リポジトリか」ではない —— `--is-inside-work-tree`（包含）はリポジトリ内の跡地で、`--show-toplevel` の照合は跡地で `git init` された場合に素通りし、どちらも同じループが 1 歩先で再現する。問い合わせ先を `repo_path` にしたのは、疑わしいパスの側で git を動かすと本物の worktree の失敗（dubious ownership 等）が「リポジトリではない」と区別できず黙って `Gone` に落ちるため。同じ問い合わせを `sync_branch` にも置いた —— `head_branch` は跡地の中で git を動かすので、外側の `main` を「エージェントが付けたブランチ」としてタスク行に書き込みうる（そのブランチは publish 済みなので掃除の削除条件を満たす）。[ADR-0010](/decisions/adr-0010-worktree-cleanup-pane-release.md) に判定 4 値目として Amendment を追記した。git が認識しないディレクトリはディスクに残す —— `git worktree remove` でも消せなかったものなので、置き換えた WARN は誰にも取れる行動を指していなかった。`git` を起動できない I/O 失敗は `Gone` に落とさず伝播させる（ディレクトリ不在と `git` 不在は `std::process` がどちらも `NotFound` で返し区別できないため、通常の「削除済み」は呼び出し側の `Path::exists` ゲートが先に落とす）。タスク行の `worktree_path` を削除時に落とす案は会話継続での worktree 再利用への影響確認が要るので別途。
