* **Update**: [orchestrator-core](/components/orchestrator-core.md) — 削除済み worktree のパスに無関係なディレクトリが 1 つあるだけで、掃除ループが 60 秒ごとに `worktree cleanup failed: git status failed: fatal: not a git repository` を出し続ける問題を直した（#694）。タスク行は削除成功後も `worktree_path` を保持する（`set_worktree` に消す口が無い）ので sweep はそのパスを永久に見に来るが、スキップ条件は `Path::exists` だけだったため、跡地にディレクトリが現れると `decide_cleanup` 冒頭の `git status --porcelain` が落ち、**正常終了したタスクについて**プロセスの生きている限り WARN が出続けていた。`decide_cleanup` の先頭に `is_worktree`（`rev-parse --show-toplevel` の出力をパス自身と照合）を入れ、パスがワークツリーの**ルート**でなければ `CleanupDecision::Gone`（= `CleanupOutcome::Gone`）として `run::finalize` が debug で抜ける。訊くのは同一性であって包含ではない —— `--is-inside-work-tree` だと跡地がリポジトリの中にあるとき true になり、以降の判定が外側のリポジトリについて答えてしまう（`git status` が外側の作業ツリーを読み、`worktree remove` は git が列挙しないパスで失敗する = 同じループが 1 歩先で再現する）。git が認識しないディレクトリはディスクに残す —— `git worktree remove` でも消せなかったものなので、置き換えた WARN は誰にも取れる行動を指していなかった。`git` を起動できない I/O 失敗は `Gone` に落とさず伝播させる（ディレクトリ不在と `git` 不在は `std::process` がどちらも `NotFound` で返し区別できないため、通常の「削除済み」は呼び出し側の `Path::exists` ゲートが先に落とす）。タスク行の `worktree_path` を削除時に落とす案は会話継続での worktree 再利用への影響確認が要るので別途。
