* **Update**: dispatch の失敗を**最大 3 回まで自動で再試行**し、**使い切ったときだけ通知**するようにした（[#492](https://github.com/tomoya-k31/totsuka/issues/492)、[orchestrator-core](/components/orchestrator-core.md)、[状態DB](/data/state-db.md)）。動機は実機で踏んだ `agent_prompt_stalled` — pane と CLI の起動までは成功し、**打鍵は入ったが submit されず** 42 秒で失敗する。同じタスクを人手で `totsuka task retry` したら内容も worktree も同じまま一発で通った（同種の観測は以前にもある）。つまり**人間の修復手順は「もう一度 retry を打つ」だけ**で、それを機械にやらせた。**上限が設計の中心である**: `requeue_conversations_with_unsent_messages` が `Failed` を除外している理由（上限も間隔も無く requeue すると毎 tick 同じ失敗を繰り返し、通知も毎回出る）はそのまま生きており、**回数を数えることがその唯一の違い**になる。逆に**何が失敗したかは一切見ない** — 上限がある以上、恒久的な失敗に 3 回使う無駄より、分類を誤って「もう一度で直る失敗」を切り捨てる害のほうが大きい。回数はプロセス内のカウンタではなく **`events` から毎回数え直す**（`StateDb::auto_retry_streak`、先例は `unknown_stop_streak`）ので、`run` の再起動をまたいでも「あと何回」が保たれ、人間の `task retry`（`detail.kind = "cli"`）が走査を止めるため**予算が自動でリセット**される。自動再試行は `detail.kind = "auto_retry"` で記録し、監査ログ上で人間の retry と区別できる — この「provenance は `detail` に入れる」という規約は `TaskEvent::Reopen` の rustdoc が既に定めていたもので、そこに相互参照を足した。**プロトコル変更なし・新しい状態なし・設定なし**（定数 3。必要になったら `[hooks].block_retry_limit` の先例に倣って出す）。通知は既存の `NotifierEvent::Failed` を使う — `NotifierEvent` に `#[serde(other)]` が無いため、新 variant を足すと旧 notifier で**通知が黙って止まる**。テストは 2 本（一過性なら人手なしで `done` に到達し `failed` 通知が出ない／恒久失敗は `task/dispatch` きっかり 4 回で止まり通知はちょうど 1 件）で、mock plugin に `dispatch_error.fail_first` を足して駆動する。どちらも修正を無効化すると落ちることを確認済み。**初版の設計は 553 行あったが、「無限ループを避けるための選別」を主眼に組み上がっていた** — 上限を付けた時点でループは構造的に起きないので、エラー allowlist・protocol 拡張・バックオフ・設定化をすべて落として 103 行に畳んだ。私が既存コメントの警告を文脈ごと持ち込んだのが肥大の原因だった。
