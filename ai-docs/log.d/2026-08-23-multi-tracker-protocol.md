* **New**: [ADR-0056 複数トラッカーは単一プラグイン内のリストで持ち、repo→トラッカーの順方向マッピングはプラグイン設定を正本にする](/decisions/adr-0056-multi-tracker-routing.md)。GitHub Project / Notion Database を複数同時に polling し、Slack 発の依頼を解決済みリポジトリに対応するトラッカーへ起票するための設計（#542）。複数プラグインインスタンス（`[plugins.github-a]`）は [ADR-0027](/decisions/adr-0027-plugin-artifact-naming.md) が却下した `name ≠ bin 名` の復活にあたるので採らず、単一プラグイン内の `[[projects]]` / `[[databases]]` リストにする。`source_name` が据え置きなので `[[workflows]].source` の結合は無傷。**タスク id が衝突しない**ことがこれを安全にしている — GitHub の issue node id と Notion の page id はグローバル一意なので、1 プラグインが複数 project/database を扱っても冪等キー `UNIQUE(source, source_task_id)` は衝突しない。
* **Update**: [plugin-protocol](/components/plugin-protocol.md) — protocol **0.5.1**: `InitializeResult.claimed_repos`（#542）。task_source が「自分がトラッカーになっているリポジトリ」と「そこへどう起票するか」を `initialize` の応答で申告する。リポジトリ → トラッカーの**順方向**マッピングで、プロトコルはこれまで逆方向（タスクの `repo_hint`）しか運んでいなかった。`ClaimedRepo { repo, destination }` の `destination` は構造体ではなく **Agent 向けの散文**にした — 消費者がコードではなくプロンプトなので、構造にすると Orchestrator が各トラッカーの形を知って文へ組み立て直す責務を負い、task_source が増えるたびにプロトコル変更が要る。**代償は明示してある**: `destination` の内容は機械検査されず、守るのは triage の検収 rubric だけで、[ADR-0045](/decisions/adr-0045-read-only-is-not-guaranteed.md) の read-only と同じクラスの保証である。additive・省略可で、**空は「このプラグインは claim しない」であって「このリポジトリにトラッカーが無い」ではない** — 0.5.1 より前のプラグインは省略で空を返すので、混同すると古いプラグインが「トラッカー無し」に見える。**patch にしたのは 0.4.1 と同じ理由**（minor は `<0.5` 上限の manifest を全部座礁させる）。ただしワイヤが互換でも `InitializeResult` は**プラグインが構築する型**なので、リポジトリ外のプラグインは再コンパイルが要る（0.4.2 の `not_released` 追加と同じ形）。
