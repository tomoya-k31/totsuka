* **Update**: [Event Gateway の構築手順](/operations/event-gateway-setup.md) の着手前チェックが**そのとおり打つと動かない**コマンドだった。`constraints/run.managed.requireInvokerIam` は managed constraint なので `gcloud resource-manager org-policies`（V1 API）では扱えず、制約を評価する前に `INVALID_CONSTRAINT_NAME` で落ちる。**「エラーが出た＝適用されていない」と読めてしまう形なので、コマンドを間違えると判定が逆に転ぶ** —— しかもここは「この構成が成立するかどうか」を決める最初のゲートである。`gcloud org-policies`（V2）に直し、さらに **`--effective` を必須**にした: 付けないと未適用のときの答えが `NOT_FOUND` という*エラー*になり、付ければ `enforce: false` と肯定形で返る。実機（tier 1 の組織 1 件）で両方の挙動を確認したうえでの修正である。`--effective` は継承と上書きを畳むので、プロジェクト単位の上書きは `--project` で別途潰す旨も足した。あわせて **OpenTofu の `image` 既定値が陳腐化する経路を塞いだ**。既定値は `…:v0.7.5` に固定されていて、ゲートウェイイメージを publish するジョブが入ったのは #660 なので、**そのタグにイメージは存在しない**。`release-please-config.json` の `extra-files` に `services/slack-event-gateway/tofu/variables.tf` を足し、`default` 行に `# x-release-please-version` を付けてリリースごとに追従させる。ただし**リポジトリ内の既存マーカーは `Cargo.toml` の裸のセムバーだけ**で、イメージタグ側は `v` 付きである必要がある（リリースジョブは `tag_name` で push する）—— release-please が `v` を保つかは初回まで分からないので、推測に賭けずに `ci.yml` の `gateway` ジョブへ**照合ステップ**を足した。`variables.tf` の既定タグが `v<ルート Cargo.toml の version>` と一致しなければ赤くする。Release PR は両方を同じコミットで書き換えるので、**ずれた瞬間に Release PR が赤くなり、デプロイする人ではなくマージする人が気づく**。`tofu validate` はこれを見られない —— 存在しないタグも文字列としては完全に妥当だからである。　Copilot レビューで、**同じ V1 コマンドが他に 3 箇所生き残っていた**のが見つかったので、そちらも直した —— `services/slack-event-gateway/tofu/README.md` / `README.ja.md`、`main.tf` の運用者向けコメント、[OpenTofu モジュール](/infrastructure/slack-event-gateway-tofu.md)。**モジュールの README から入る読者は、直したはずの誤りをそのまま踏む**経路が残っていた。あわせて `--organization` と `--project` が排他であることを明記し（「でも同じ問い合わせを」と書いていたので両方付けると読めた）、`tofu apply` の前に `docker manifest inspect` でイメージの実在を確かめる手順を足した —— **存在しないタグは `tofu plan` も `tofu validate` も通り、失敗するのは apply の最後**、Cloud Run がリビジョンを起動しようとした時点だからである。release-please への登録が効くのは次のリリース以降なので、それまでの窓はこの検査で埋める。
