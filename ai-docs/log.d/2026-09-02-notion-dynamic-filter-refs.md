* **Creation**: [ADR-0066 trigger.filter の動的な値は @&lt;name&gt; の名前付き lookup で解決する](/decisions/adr-0066-notion-dynamic-filter-refs.md)（#606）。`[notion.dynamic.<name>]` に生の Notion filter で lookup 規則を置き、`trigger.filter` 内の `@<name>` を poll ごとに 1 ページの id へ解決する。

* **Update**: [config-reference](/development/config-reference.md) に `[notion.dynamic.{name}]` の節を追加し、`[notion]` のキー表にも行を足した。生成物の `docs/config-reference.md` / `.ja.md` も更新した。

* **Note**: **Notion のクエリフィルタは、クエリ対象の DB のプロパティしか読めない。** relation 越しの条件が書けないので、「現在のスプリントのタスクだけ拾う」は**そのスプリントの page id 直書き**しか手段が無かった。id は 2 週間ごとに変わり、書き換えを忘れると**取り込みが 0 件になる。エラーも警告も出ない** —— フィルタは有効な id 形式のままで、Notion は素直に「該当なし」を返し、`config validate` も `doctor` も緑である。設定に「今期の答え」を書かせる形だったのが原因で、規則を書かせる形へ移した。

* **Note**: **0 件と 2 件以上はどちらもエラーにして、縮退させないと決めた。** ここが設計の中心である。「解決できないので条件を落とす」を選ぶと**フィルタが消えてデータベース全体が取り込まれる** —— 一番派手な事故が成功の見た目で起きる。2 件以上で先頭を採らないのも同じで、ページが本当に 2 つのスプリントを指しているときに任意の一方を黙って選ぶのは誤りである。`Err` は poll を失敗させ、運用者に毎周期エラーが出る。それが「評価できない条件を書いている」ことの正しい代価である。

* **Note**: **参照名を `[a-z0-9_]+` に限ったのは、未宣言の参照をエラーにできるようにするため。** `@` で始まるリテラル（`@example.com` / `@Channel`）を名前空間から外しておくと、「宣言の無い `@name` は `initialize` で落とす」を安全に強くできる。放置すればタイポが Notion へリテラルとして送られ、何にも一致せず取り込み 0 件になる —— #606 が直そうとしている壊れ方の再生産である。

* **Note**: **検査は `trigger.filter` の部分木だけを歩く。** トリガー表全体に広げると `assignee = "@me"` を未宣言の参照として読んでしまう（`@me` は #572 の assignee 語彙）。2 つの名前空間は**予約語表ではなくスコープで**分けた —— 予約語表にすると `plugin_sdk::AssigneeFilter` と歩調を合わせ続ける義務が生まれる。

* **Note**: **poll を跨ぐキャッシュは持たない。** lookup の答えが変わることが存在理由なので、キャッシュには staleness ポリシーが要るが、スプリントが切り替わる時刻を config は知らないため正しい TTL を選べる者がいない。代価は「参照している名前 × workflow 数」のクエリが毎 poll 増えることだけ。

* **Note**: **Notion 側に派生列（rollup / formula）を足す道は今も有効で、触れるボードならそちらが安い**（totsuka に何も足さずに済む）。この機能は「共有本番ボードのスキーマを触れない」場合のためにある。両立するので禁じていない。
