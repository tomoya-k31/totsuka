* **Creation**: [ADR-0072 Slack イベント受信を Events API + Cloud Run + Pub/Sub へ移譲する](/decisions/adr-0072-slack-event-gateway.md) — totsuka 停止中の取りこぼしと購読の自動無効化（#652）を、Socket Mode リレーではなく Events API への転換で解決する決定。常時稼働ホストを持たない構成、`event_source` による Socket Mode の併存、利用者ごとのパスとトピックによる複数人分離、グループメンション対応、イベントゲートウェイの配布形態を決めた。**保存対象は「自分に関係しうるもの」だけに絞った** — 全件の座標を publish する案は、イベント購読がアプリ単位であるため**全社チャンネルの 1 投稿が利用者の数だけ別々に配信される**ことに気づいて取り下げた。利用者 5 人なら同じ発言の座標が 5 本のトピックに入り、自分と無関係な発言の履歴が人数倍で 7 日間滞留する。費用は月 1 ドル未満のままなので、これは費用ではなく「置かなくてよいものを置かない」の判断である。代わりに publish するのは、自分の user id に完全一致するメンションタグを含むメッセージ・**任意**の `<!subteam^S…>` を含むメッセージ（所属判定は totsuka 側にあるのでここでは絞れない）・`reaction_added`・`block_actions` の 4 種だけにした。**チャンネル監視はこの絞り込みと両立しない**ので、`event_source = "gateway"` では `conversations.history` の定期ポーリング（`watch_poll_interval_secs`、既定 60）に移す — [ADR-0068](/decisions/adr-0068-channel-watch-trigger.md) の起動時 backfill を周期実行に広げるだけで新しい機構を作らない。監視チャンネル一覧をクラウドに持たせる案は、ずれたときの症状が「監視が黙って効かない」なので取らなかった。**遅延が増えるのはチャンネル監視だけ**で、他の経路は Pub/Sub の long-poll のまま Socket Mode との差が 1〜2 秒に収まる。あわせて、絞り込みを入れたことで**イベントゲートウェイのフィルタが関門になった** — 通らなかったメッセージはレコードが存在せず totsuka から永久に見えない。判定の権威は `fetch_message` 後の `mention.rs` に残るので偽陽性は無害だが、偽陰性はメンションが黙って消える唯一の致命傷になる。この非対称をそのまま検査要求に写すため、契約は見本 JSON ではなく**適合テストスイート**（Slack の生ペイロード → 期待される Pub/Sub レコードの組）として置き、両側の CI が通ることを要求する。見本 1 組では形のズレしか捕まらず、「この本文からこのフラグが出るはず」という判定ロジックのズレが通り抜けるため。
* **Update**: [ADR-0072](/decisions/adr-0072-slack-event-gateway.md) を PR #664 のレビュー指摘で 9 点直した。設計を変えたのは 3 点。① **Interactivity & Shortcuts の Request URL を見落としていた** — `block_actions` は Events API のイベントではなく別の設定項目に送られるので、両方を同じゲートウェイに向けないと**承認・リポジトリ選択のボタンが一切届かない**。Socket Mode ではどちらも同じ WebSocket で届くため区別が要らず、そのまま HTTP に移して落としていた。② **`block_actions` の保持「数分」は `response_url` の寿命 30 分より短く、まだ有効なボタン操作を捨てる**ので 35 分に伸ばし、期限切れ判定は消費側に置いた（保持は取りこぼさないため、期限切れ判定は無駄に処理しないためで役割が違う）。③ **fetch 条件を `mentions_me` だけにすると、subteam メンションだけのレコードは偽のままなのでグループメンションが丸ごと素通りする** — `subteam_ids` が非空のものも fetch 対象に含めた。残る 6 点は記述の誤りと甘さ。**東京（asia-northeast1）は Cloud Run の tier 1** で、tier 2 の 1.4 倍としていたのは誤り（表の数値は tier 1 で計算済みだったので、本文と表が食い違っていた）。**Pub/Sub のサブスクリプション保持期間の上限は 7 日ではなく 31 日**（既定が 7 日）。`reaction_added` を無条件に通す記述は、`reaction.rs` が持つ「操作者本人のリアクションのみ」の不変条件（[ADR-0025](/decisions/adr-0025-reaction-task-trigger.md)）と噛み合わず、消費側が必ず捨てるレコードを保存することになるので `user` 一致で絞った。「外部 API への発信を持たない」は Pub/Sub publish 自体を禁止してしまうので「本文の処理のために外部 API を呼ばない」に限定。**「スキーマに本文フィールドが無いので漏れる経路が作れない」は言い過ぎ** — 差し替えられたゲートウェイはメモリ保持もログ出力も別宛先への送信もできるので、スキーマとは独立にテストで守る振る舞いだと書き直した。**200 を返してよいのは publish が受理された後だけ**（先に返せばイベントは永久に失われ、失敗を返せば自動無効化の条件に近づく）。配送同一性の導出規則が契約に無かったので `kind` ごとに定義して適合 fixture に載せることにした。なお REST `pull` を long-poll として扱う点への異議は**採らなかった** — 公式の規定は "the system may wait (for a bounded amount of time) until at least one message is available" で待つ挙動は存在する。ただし "may" なので保証ではなく、空応答を即座に再要求するループとバックオフを実装側の要件として明記した。
