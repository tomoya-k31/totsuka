* **Update**: core のプロンプト上書き面 15 キーを削除し、`[[workflows]].rubric` 1 キーへ絞った（[#465](https://github.com/tomoya-k31/totsuka/issues/465)、[ADR-0023 の Amendment](/decisions/adr-0023-configurable-prompt-surface.md)、[orchestrator-core](/components/orchestrator-core.md)、[設定リファレンス](/development/config-reference.md)、[フックのセキュリティ](/security/hook-security.md)）。**破壊的変更**。`[prompts]`（8 キー）と `[[workflows]].prompts`（7 キー）が消え、優先順位の梯子は 5 段から 3 段（`workflow.rubric` > profile 既定 > 組み込み）になった。**消したのは「グローバルな段」であって梯子の順序ではない** — キーを 1 つ書くだけで後から入った profile の検収が黙って無効化され（`[prompts].verification_rubric` で triage が URL 検収を失い、`[prompts].marker_self_report` で design / implement が確認プロトコルを失う）、症状が「検収が緩くなる」方向へ倒れていた。順序を逆にすると今度は profile が運用者の選択を黙って覆すので、どちらの順でも黙って壊れる。残した `rubric` はワークフロー単位なので、運用者が見ていないワークフローに届かない。**残す綴りは `verification_rubric` ではなく `rubric` を選んだ** — issue は前者のほうが名前として一貫していると書いていたが、後者は #314 より前からあり実運用が実際に使っている唯一のキーで、そちらへ寄せると `[[workflows]].prompts` テーブルごと消せる（issue の提案は 1 キーのためにテーブルを残す形だった）。廃止キーは**パースはされ検証で落ちる**: 素の `unknown field` は「そのキーは無い」としか言わないので、キーごとに何になったかを名指しする `RemovedPromptKey` を用意した。移行期間は置かない（既存ファイルの母数が 0）。`ALLOWED_PLACEHOLDERS` と組み立て検証は残り、**検査対象が「運用者が書いた値」から `defaults.toml` 自身へ移った** — 全ビルドに載るアセットのプレースホルダは従来まったく無検査だった。ADR-0023 は supersede ではなく amend で、撤回したのは決定 1 の後半だけである。`include_str!` ゆえリビルドが要る点（ADR-0023 の Context がまさに問題視していたこと）は**意図的に受け入れ直した**。プラグイン側の `[prompts]`（slack 11 キー・github / notion）は対象外 — 悪い上書きの被害が返信案の質低下に留まり完了検知を壊せないため。
