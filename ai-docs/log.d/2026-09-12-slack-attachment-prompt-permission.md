* **Update**: [task-source-slack](/components/task-source-slack.md) の添付セクションが、**エージェント自身の経路を塞がない文面**になった（[設定リファレンス](/development/config-reference.md) の `body_attachment_header`）。実機検証で「エージェントは permalink から file id を切り出して自力で中身を読む」ことが分かった一方、**出荷している既定文はその逆を指示したままだった** —— 「名前・種類・サイズだけが分かっています」と列挙して permalink を数に入れず、「添付を読めていないことを返信に書いてください」と言っていた。唯一動く経路からエージェントを遠ざける文面である。既定文を「添付ファイルの中身はこのタスクに含まれていません／リンクが付いている添付はそこから自分で取得できる手段があれば使ってください／取得できなかった場合やリンクが無い添付は推測で補わず、読めていないと書いてください」の 3 段に組み直した。**②を条件形にしているのは `permalink` が `Option` だから**で、リンクが載らない添付に無条件の指示を出すと存在しない handle を指すことになる。**主語にシステム名を出さないことも決めた** —— エージェントが受け取るのはメンションとスレッド文脈だけで、`totsuka` という語はその世界に無い。この文面の初稿が全プロンプト既定値の中で唯一の例外だったので、再発しないよう `defaults.toml` のコメントに理由ごと残した。**ツール名は意図的に出さない** —— 名指しすると、それを持たないエージェントに存在しない道具を探させる。あわせて **スレッド文脈行にも permalink を載せる**ようにした（`（添付: <name> <permalink>）`）: 名前だけの行は file id が取れず、エージェントにとって行き止まりで、起点メッセージの添付だけが読めてスレッド内の添付は読めないという非対称ができていた。コード側の doc コメント 4 箇所（`the content never reaches the agent` / `the agent cannot fetch it` 等）も**実機の事実と正面から食い違っていた**ので直した。デフォルト検査は「中身を取得していません」と「自分で取得できる手段があれば使ってください」の**両方**を pin する —— 片方だけでは、どちらの半分が落ちても検査が通ってしまう。
