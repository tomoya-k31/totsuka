* **Update**: [task-source-slack](/components/task-source-slack.md) の添付メタデータ（#642）を実機で確認し、**設計の前提を 2 つ確定させた**。① **メタデータの取得に `files:read` は要らない** —— 付与スコープが `identify channels:history groups:history channels:read groups:read reactions:read users:read chat:write im:write`（`files:read` 無し）の状態で、`files` 配列が名前・MIME・サイズ・permalink すべて揃って届いた。#642 の実装は「manifest に `files:read` が無いので中身は取得できない」と書いていたが、**メタデータ側にスコープが要るかどうかは未確定のまま出していた**ので、ここが確定した意味は大きい（要るなら Step 0 のためだけにアプリ再インストールが必要だった）。② **permalink を本文に置くだけで、Slack MCP を持つエージェントは中身を自力で読む** —— `answer` profile（Bash 全面 deny・`--permission-mode plan`）のエージェントが、本文の permalink のパスから file id を切り出し、MCP の `slack_read_file` を呼んで添付を読んだ。**当初「次の段」として想定していたプラグイン側のダウンロード（`files:read` 追加 + アプリ再インストール + ローカルパス渡し）は、これで必須ではなくなり保険に格下げされる**。ただし**自力で読めるのは起点メッセージの添付だけ**で、保険が要る場面は 4 つ残る: `permalink` は `Option` なので欠ければ本文行から黙って省かれる、**スレッド文脈側の添付は名前だけで permalink を持たない**、MCP を持たないエージェント、MCP の認証切れ。副次的に、**`answer` の deny セット（ファイル編集・シェル）と plan モードの下でも MCP 経由の読み取りは通る**ことも分かった。
