* **Update**: [task-source-slack プラグイン](/components/task-source-slack.md) のメンション判定を**個人 + ユーザーグループ**まで広げた（#658、[ADR-0072](/decisions/adr-0072-slack-event-gateway.md) 決定 8）。`mention.rs` の判定は `<@U_ME>` と `<@U_ME|` の 2 パターンだけで、チームの担当として `@team-name` で名指しされてもタスクにならなかった。**所属判定は totsuka 側に置く** —— エッジ（イベントゲートウェイ）で真偽値にするには運用者の所属グループ一覧をクラウド設定に持たせる必要があり、メンバー変更のたびに人が書き換える二重管理になり、陳腐化すると**メンションを黙って取りこぼす**。ゲートウェイは本文からグループ ID を抽出するだけにして、自分が属するかは totsuka が `usergroups.list`（`include_users=true`）を**起動時に 1 回**呼んで決める。定期更新は入れない —— メンバー変更は稀で再起動が追従し、本 ADR の前提どおりノート PC は頻繁に止まって起動するので起動時解決は実質かなり頻繁に走る。**`<!here>` / `<!channel>` / `<!everyone>` は対象外**（名指しではなく「この場にいる人へ」で、タスク化すると雑音が支配的になる）。タグの抽出は `gateway_contract::extract_subteam_ids` を**ゲートウェイの前置フィルタと共有**しているので、「何がグループタグか」で両者がずれようがない —— ゲートウェイは**任意の**グループ ID で publish し、そのうちどれが自分のものかをここが決める、という分業になる。**`usergroups:read` が無いときは起動を止めず、個人メンションのみに縮退して警告する。** 止める案も採れたが、`check_scopes` が既に同じ判断をしている（「プラグインは本業を続けられる。使っていないかもしれない機能のために動いている設定を落とさない」）ので揃えた。ただし**この警告だけは無条件**である —— 他のスコープ警告は「設定が要求しているのに無い」で発火するが、グループメンションには有効化する設定が無いので、不在を免罪できる設定項目が存在しない。症状は「個人宛は動くのにグループ宛だけ 1 件も来ない」で、気づきにくい側に倒れる。適合スイート側には**非対称性を端から端まで検査するテスト**を足した: `message` の全ケースについて「`mention.rs` が受け入れるなら、ゲートウェイは必ず publish していること」を要求する（逆向きは許す —— 余分な `fetch_message` 1 回で済み、メンションを失うのはこの向きだけである）。`manifest.yml` と `manifest.gateway.yml` の user scope に `usergroups:read` を足した。**スコープ追加は再インストールを要求し、`xoxp-` と `xoxb-` の両方が再発行される。**
