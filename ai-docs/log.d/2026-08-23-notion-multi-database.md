* **Update**: [task-source-notion](/components/task-source-notion.md) — #542: Notion Database を**複数**同時に polling できるようにし、リポジトリ → データベースの対応をそこから作るようにした（[ADR-0056](/decisions/adr-0056-multi-tracker-routing.md)）。トップレベルの `database_id` は **`[[databases]]` の配列**（各要素が `database_id` + `repos`）へ移った。`property_map` / `status_map` / `priority_map` / `in_progress_statuses` / `body_source` / `prompts` / `token` はトップ共有のまま。github 側（`[[projects]]`）と同じ形である。
* **Update**: **`repos` によるフィルタは github と非対称で、条件付きにした。** GitHub の issue は必ずリポジトリを持つが、Notion のページの `repo_hint` は**任意プロパティ**なので、値が無いページはそのまま取り込む（Orchestrator が従来どおり F-11 で解決する）。落とす設計にすると、`repo_hint` をマップしていない利用者は**1 件も取り込めなくなる** — 「フィルタなのだから一律に適用する」と書くほうが揃って見えるが、材料が無い側で適用すると全滅する。`repos` 自体は必須・非空で、これは claim の材料としての役割による。
* **Update**: **`task/update_status` はページの親データベースを Notion に問い合わせる。** PATCH 先はページ id だけで足りるが、その前に「対象 option がそのデータベースに存在するか」を検証しており、どのデータベースかは request が語らない。ingest 時のメモを先に引き、無ければ `GET /pages/{id}` の `parent.database_id` を読む。**各データベースの option を順に試す方式は採らない** — 別のデータベースにだけ存在する option を通してしまい、明確な「unknown status」エラーが Notion API 側の分かりにくい失敗に化ける。id は**ハイフンの有無を無視して**突き合わせる（Notion は両形式を受け付け、ハイフン付きで返すので、設定をハイフン無しで書くと素の比較では永久に一致しない）。
* **Update**: **`config/validate` は全データベースを見るようにした。** `property_map` は全データベース共通なので、あるデータベースだけがマップ先プロパティを欠いていると**そこ由来のタスクだけ**が壊れる。1 つ目だけ見て緑にするのが一番静かな壊れ方になる。
* **Update**: **Notion への書き込みは Agent 環境の Notion MCP 等が前提**であることを claim の `destination` に書いた（totsuka は Notion ページを作らない）。`destination` には `database_id` に加えて `property_map` の列名（title / status / repo_hint）を載せる — 列名は運用者が付けたもので、ページを作る Agent には推測できないため。
