* **Fix**: クラッシュ窓中に queue されたタスクが、**プラグインの復帰を待たずに終端 `Failed` へ落ちる**問題を直した（[#499](https://github.com/tomoya-k31/totsuka/issues/499)、[ADR-0051](/decisions/adr-0051-plugin-supervision.md) に節を追加、[orchestrator-core](/components/orchestrator-core.md)）。クラッシュした `Plugin` は再起動が**成功**するまでエンジンのマップに残るので、`resolve_dispatch_target` が capability しか見ないと**死んだハンドルへ dispatch が解決する**。**2 つの時計が噛み合っていない**: dispatch の自動再試行は `DISPATCH_RETRY_LIMIT` 回 × `SETTLE_TICK` 間隔で 1 秒未満に尽きるのに、最初の再起動バックオフだけで 1 秒ある。**#495 の PR で一度実装して取り下げた** — 素朴に park すると `crash_on_dispatch`（その dispatch 自体がプラグインを殺すケース）でタスクが終端へ行かなくなり、既存テスト 2 本（`e2e_agent_crash_fails_task_and_orchestrator_survives` / `failed_hook_dispatch_rolls_back_reserved_session`）が壊れた。**今回の要点は「エージェントの状態だけでなく、そのタスク自身の再試行回数も見る」こと**である。停止中でも**そのタスクの自動再試行が 0 回なら park**（スロット解放・`Queued` のまま）、**1 回以上なら通常の経路で予算を使い切らせる**。この差が `crash_on_dispatch` を救う — **まだ何も試していないタスクは他人のクラッシュの巻き添えなので待てばよく、自分の dispatch が失敗し続けているタスクは自分が原因かもしれないので予算を使い切るべき**である。加えて**見放し済み**（予算切れ / `restart = false` / spec 未記録）のプラグインは `Failed`（「再起動されない」と名指しする）— これが無いと park が無限になる。`abandoned_plugins` は**`escalate_dead_plugin` の中で立てる**: 呼び出し側 3 箇所に書くと「諦めた」と「dispatch がそれを知っている」がずれる。**liveness の判定は capability ゲートより先**に置く（死んだプロセスの宣言した capability は宣言のままなので、先に見ると間違った問題を、しかも終端の `Failed` として報告する）。`first_backoff` を縮める案は確率を下げるだけで構造ではないので採らない。報告は `blocked_on_agent` でタスクごとに 1 回だけ（先例は `blocked_on_tools`。200ms ごとに同じ警告を出さない）。テストは pure な 4 分岐 2 本 + e2e 1 本で、**e2e はクラッシュ窓を実際に作る** — mock source に `submit_delay_ms` を足し、タスクの到着をエージェントのクラッシュ**より後**に置いた。**最初に書いた e2e は即時 submit で、検知と競合して落ちていた**（失敗理由も `/nonexistent` での git 失敗であってゲートではなく、DB の `events` を読むまで誤診していた）。**タイミングで通ったり落ちたりするテストは、振る舞いを検証していない。** **そしてそれを言った直後、書き直した版もまだ時間依存だった** — `submit_delay_ms` で順序は決めたが、停止条件が固定ウィンドウのままで、CI の負荷次第で `submitted == 1` に届かない余地が残っていた（レビュー指摘）。**park そのものを待つ**ように変えて解消した（park の warn ログを条件にする）。「submit されたこと」を待つのでは足りない点も重要で、**dispatch が一度も試されないまま `failed == 0` が通ってしまう** — 緑だが何も証明しないテストになる。結果としてテストは 2.2 秒 → 1.0 秒に縮み、主張も「失敗しなかった」から「park された」へ強くなった。park を無効化すると落ちることを実測済み（旧版は `failed: 1`、新版は条件未到達）— どちらも #499 の症状そのものである。**レビューで 7 件出た。最大のものは、park がスロットを取り続けて健全なエージェントを飢えさせる**という点である — `plan_dispatch` はサイクル単位で計画を確定するので、`dispatch_one` の park arm で解放しても遅い。`max_concurrency = 1` なら、クラッシュしたエージェント宛のタスクが 200ms ごとに唯一のスロットを取っては park し、**健全なエージェント宛のタスクが outage の間ずっと dispatch されない**。修正前はそれらが 600ms で `Failed` になって競合から抜けていたので、**ゲートを前に出さずに park すると、1 つのバグをより悪いバグに置き換える**ことになる。既存コメント（`dispatch_ready` の tool ゲート）が「`dispatch_one` ではなくここで弾けばスロットを取らない」と既に書いており、置き場所は示されていた。規則は `agent_gate` という純粋関数に切り出し、**フィルタと resolver の両方から呼ぶ**（2 箇所に複製すると、どちらも単体では妥当に見えるまま drift する）。**この修正には最初テストが無かった** — `dispatch_one` 側の park arm が残っているため、フィルタのゲートを外しても既存 e2e は通ってしまう。飢餓そのものを捕まえるテスト（`max_concurrency = 1`・死んだ agent と生きた agent・実リポジトリ）を足し、ゲートを外すと 30 秒待って落ちることを実測した。**次に重いのは、`auto_retry_streak` の DB エラーに warn を出すという修正が、コミットメッセージと本 log とレビュー返信の 3 箇所で「やった」と書かれていながら実際には入っていなかったこと。** python の置換スクリプトで 2 つ目の sub が失敗し `write_text` に到達せず 1 つ目も適用されなかったのに、再確認しなかった。**握り潰しを直すコミットで、自分の主張を握り潰していた。** 残り: `blocked_on_agent` は park 以外の結末で消すだけでは不十分（workflow 削除や cancel でループに入らないタスクが残る）なので、**毎サイクル queued 集合で刈り取る**構造にして境界を構造的にした。ADR の Consequences が「クラッシュ窓中のタスクも含む」と全面的に書いていたのを「まだ何も試していないタスクに限る」へ狭めた（**クラッシュの原因に最も近いタスク**＝その dispatch でプラグインが死んだものは streak ≥1 なので対象外で、そこには #499 の症状が残る）。ADR のテスト本数の誤り、`resolve_dispatch_target` の rustdoc（`agent_caps` という古い引数名と「順序は副作用版と同じ」という記述。後者は #499 が意図的に破っている）、`submit_delay_ms` が read ループ全体を止めて `suicide` も同じだけ遅らせる点の明記。**そして CI で落ちた。** log を捕まえるテストヘルパが `set_global_default` の失敗を `let _ =` で握り潰しており、**同一プロセス内で 2 つのテストが呼ぶと先に登録した方だけが勝ち、もう片方は空のバッファを読む**。**ローカルの `dev-test.sh` は nextest（テストごとに別プロセス）、CI は `cargo test --workspace`（1 プロセス内スレッド）**なので、**ローカルのループはこの種の「プロセス状態を共有する」バグを構造的に検出できない**（[ADR-0049](/decisions/adr-0049-local-test-loop.md) の選択の帰結）。subscriber をプロセスで 1 回だけ設置し、各テストは自分の開始オフセット以降だけを読む形に直した。設置失敗は `expect` で大きく落とす。さらに `cargo test` では**兄弟テストが同じバッファへ並行に書く**ため、「全文に A が含まれ、かつ B が含まれる」は別々のテストの行で満たされうる — **1 行に同時に含まれること**を要求し、少なくとも一方が自テストのプラグイン名を指すようにした。そのために park の warn へ `agent` フィールドを足したが、これはテストの都合ではなく**運用上も「どのエージェントが down か」が要る**情報である（`dispatch_one` 側で最初 workflow 名を `agent` として出しており、フィールド名が嘘になっていたので実 agent 名を引くよう直した）。**教訓は「CI と同じコマンドで確かめる」に尽きる** — `cargo test -p … --test …` を一度打っていれば push 前に分かった。
