* **Update**: [ADR-0072](/decisions/adr-0072-slack-event-gateway.md) に決定 11「信頼境界を経路 A と経路 B に分ける」を追加し、**Status に書いていたブロッカーを訂正した**。当初「ドメイン制限共有が有効だと Cloud Run を公開できず、回避策の外部ロードバランサで月 18 ドル、費用前提が 20 倍になる」と書いていたが、**どちらも誤りだった**。① **外部 LB では解決しない** — Serverless NEG 経由で LB から届くリクエストも Cloud Run には認証情報なしで到達するので、結局 `allUsers` への `roles/run.invoker` 付与が必要になる。LB が解くのは ingress の制限であって IAM ではない。月 18 ドル払って何も解決しない選択肢だった。② **無料の正規手段がある** — Cloud Run の Invoker IAM チェック自体を無効化する（`--no-invoker-iam-check` / `invoker_iam_disabled = true`）。Google のドキュメントがドメイン制限共有下での推奨手段として明示している。**組織ポリシーは一切緩めずに済み、ブロッカーではなくデプロイ時のフラグ 1 つ**に格下げされた。決定 11 を足したのは、この訂正の過程で**経路を混同すると強化したつもりで配信を壊す**ことが分かったため。**totsuka はイベントゲートウェイに一度も接続しない**（Pub/Sub から直接引く）ので、2 本の経路は性質がまったく違う。経路 A（Slack → ゲートウェイ）は Slack が IAM プリンシパルになれない以上**公開が不可避**で、関門は推測不能パス + 利用者別 signing secret + タイムスタンプ窓しかない。**IP 許可リストは採れない** — Slack は Events API の送信元 IP の安定した一覧を公開しておらず（"Allowed IP ranges" は逆向きの機能）、推測で組めば配信が落ちて**この ADR が解決しようとしている購読の自動無効化が再発する**。経路 A において IP 制限はセキュリティ強化ではなく可用性リスクである。経路 B（totsuka → Pub/Sub）は outbound pull なので Workspace アカウント単位で制御でき、**ドメイン制限共有が本来の仕事をするのはここ**。鍵は配らない（ADC なら失効・期限・複製追跡のどれも鍵より強い）。「会社 IP 限定」を課すなら VPC Service Controls でこの経路に付けられるが、自宅・外出先から引けなくなり「ノート PC は止まるし移動する」という本 ADR の前提と衝突するため、採否は運用者に委ねる。
* **Update**: 上の決定 11 を PR #666 のレビュー指摘で 4 点補強した。**一番重かったのは、DRS の関門表が経路の混同を自分で作っていたこと** — 「IAM プリンシパル全般 → DRS で個人・他社を拒否」と書いたので、Invoker IAM チェックを無効化した経路 A の公開エンドポイントでも DRS が守ってくれるように読めた。実際には経路 A では Cloud Run が IAM プリンシパルを一切評価しないので DRS が効く余地が無く、働くのは経路 B の Pub/Sub など**実際に IAM を評価するリソース**だけである。この決定が防ごうとしている取り違えを、決定本文の表がやっていた。次に、**タイムスタンプ窓を「既に決定済み」と書いていたが ADR 内で初出**で、値も参照先も無かった。Slack の正典に合わせて **5 分**と定め、署名比較は**定数時間の HMAC compare**（文字列の直接比較はしない）であることも明記した。残り 2 点は、`description` が「署名が唯一の関門」と要約していて index だけ読む人がパスの秘匿とリプレイ防止を不要と誤読しうる点（3 要素を表す記述に直した）と、訂正の根拠となる出典が `sources` に無かった点（Cloud Run の未認証アクセス・ドメイン制限共有・Slack の署名検証の 3 本を追加し、本文から脚注で引いた）。
