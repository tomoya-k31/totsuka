* **Update**: [ADR-0072](/decisions/adr-0072-slack-event-gateway.md) に決定 11「信頼境界を経路 A と経路 B に分ける」を追加し、**Status に書いていた公開方法を訂正した**。当初「ドメイン制限共有が有効だと Cloud Run を公開できず、回避策の外部ロードバランサで月 18 ドル、費用前提が 20 倍になる」と書いていたが、**どちらも誤りだった**。① **外部 LB では解決しない** — Serverless NEG 経由で LB から届くリクエストも Cloud Run には認証情報なしで到達するので、結局 `allUsers` への `roles/run.invoker` 付与が必要になる。LB が解くのは ingress の制限であって IAM ではない。② **無料の正規手段がある** — Cloud Run の Invoker IAM チェック自体を無効化する（`--no-invoker-iam-check`）。Google のドキュメントがドメイン制限共有下での推奨手段として明示している。**ただし確認は依然として要る。対象が変わっただけである** — 管理者は `constraints/run.managed.requireInvokerIam` でこの無効化そのものを制限でき、既定では未適用だが、適用されていれば DRS が `allUsers` を拒否したまま逃げ道も塞がれて**元のブロッカーが丸ごと戻る**（そのとき外部 LB も助けにならない）。決定 11 を足したのは、この訂正の過程で**経路を混同すると強化したつもりで配信を壊す**ことが分かったため。**totsuka はイベントゲートウェイに一度も接続しない**（Pub/Sub から直接引く）ので、2 本の経路は性質がまったく違う。経路 A（Slack → ゲートウェイ）は Slack が IAM プリンシパルになれない以上**公開が不可避**で、関門は推測不能パス・利用者別 signing secret・5 分のタイムスタンプ窓の 3 つしかなく、**いずれもコンテナの中で評価される**。したがって署名で弾いたリクエストもコールドスタートも課金対象で、費用の前提は `min-instances = 0` だけでなく **`max-instances` の上限**も含む。**IP 許可リストは採れない** — Slack は Events API の送信元 IP の安定した一覧を公開しておらず（"Allowed IP ranges" は逆向きの機能）、推測で組めば配信が落ちて**この ADR が解決しようとしている購読の自動無効化が再発する**。経路 A において IP 制限はセキュリティ強化ではなく可用性リスクである。**DRS が守るのは経路 A ではない** — Invoker IAM チェックを無効化した経路 A では Cloud Run が IAM プリンシパルを一切評価しないので、DRS が働くのは経路 B の Pub/Sub など実際に IAM を評価するリソースだけである。経路 B は outbound pull なので Workspace アカウント単位で制御でき、鍵は配らない（ADC なら失効・期限・複製追跡のどれもサービスアカウントキーより強い）。「会社 IP 限定」を課すなら VPC Service Controls をこの経路に付けられるが、自宅・外出先から引けなくなり「ノート PC は止まるし移動する」という本 ADR の前提と衝突するため、採否は運用者に委ねる。
